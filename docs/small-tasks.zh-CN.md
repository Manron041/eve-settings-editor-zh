# 小任务台账

这里存放开发者想*最终*完成的小型、非紧急改进。它们本身**不**阻塞里程碑——
只是锦上添花的项目，会在**每个里程碑结束时重新审视**，发布前逐项权衡是否
纳入该次发布。

工作流程：
- 条目出现时就加到这里，最新的放在 **Open（未决）** 的任意位置。
- 每个里程碑结束时（发布前），与开发者一起复核每条 **Open** 条目，考虑是否纳入。
- 条目发布后，把它连同纳入它的里程碑一起移到 **Shipped（已完成）**。

- [x] **读取启动器日志失败被报告成"你的日志什么也没说"。**
  `AccountsView.svelte:233` 用 `.catch(() => {})` 吞掉了启动器的读取错误，
  而下一行的 `.finally` 无论结果如何都把 `launcherState.loaded = true`，
  于是*抛出异常*和*成功读取但什么都没找到*以完全相同的方式到达空状态——
  `proposals` 为空、`loaded` 为 true。于是消息告诉用户他们的日志里什么都没有，
  而真相是读取失败了。这是账号空状态可能触发的四个原因中的第四个，也是唯一
  一个属于错误而非事实的原因；另外三个是措辞问题，已作为独立条目追踪。
  2026-08-14 在所有者的安装上诊断：启动器恰好列出 30 个角色，这 30 个全部
  已配对，所以那里诚实的说法是"30 个全部已配对"。修复方案：保留这个 rejection，
  并让空状态区分*读取失败*与*读取成功、没有新内容*。顺手让
  `launcher_proposals` 报告启动器列出了多少个角色——这正是"已配对"情形所需要
  的信息。重新设计没有动 `launcher.rs` 和 `launcher.ts`，所以后端部分无冲突。
  在 0.35.0 实机检查中看到过，有意没有因此阻塞。_添加于 2026-08-14（UI 重新
  设计实机检查）；完成于 2026-08-15。_

  **被吞掉的错误不需要新状态就能区分。** 显而易见的修复是加第三个标志表示
  "读取失败"；真正的修复更小也更好。`loaded = true` 从 `.finally` 移进了
  `.then`，于是读取失败就简单地保持**未加载**状态——空状态那句话永远不替它
  发言（只有错误会被渲染出来），而且顺带的免费好处是**重新打开面板会重试
  读取**，吞错版本永远做不到这一点，因为它已经宣布自己加载完了。rejection
  被保留，并通过现有的错误 `InlineMessage` 浮现出来。

  后端现在返回 `LauncherReport { proposals, known }`（`launcher.rs:379-400`），
  其中 `known` 汇总启动器名单里的角色列表——这是一个独立的计数，因为第 3 遍
  让这些列表互不相交。这把四个原因变成了三个诚实的结果：`known == 0` 表示
  日志什么也没说（原因 1 和 2 都属此列），`known > 0` 且没有可提议的条目时
  表示 **"你 EVE 启动器列出的全部 30 个角色都已配对"**（原因 3，这个成功情形
  过去说的却与真相相反），而抛出异常时只显示错误（原因 4）。单复数形式由
  测试钉死，所以 `known == 1` 绝不会读作"全部 1 个角色"。仅屏幕外的提议有意
  保留原始措辞——它们并不是"已配对"，而"日志对*这些*账号什么也没说"在那里
  字面上就是真的。

  **再次改动 `launcher_proposals` 之前值得知道：它有第二个消费者。**
  `AppMenu.svelte` 的提议计数徽章读的是同一条命令，所以返回形状的改动波及
  `api.ts` 和四个 spec 文件。曾提议让第二条命令返回同样的数据，被否决了，
  那会永远留下两种询问同一问题的方式。
