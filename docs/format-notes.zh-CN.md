## 按操作码的编码细节（对照 marshal.c 验证）

### 流帧结构

- 字节 0：魔数 `0x7E`；是其他任何值（或总大小 < 6）都会使 reverence 回退到 cPickle（marshal.c:467-475）。最小流大小为 6 字节。
- 字节 1-4：`shared_mapsize`，按**有符号** i32 LE 读取（marshal.c:478；实践中非负）——流中共享对象的数量。
- 边界检查：`5 + shared_mapsize*4 <= size`（marshal.c:482）。
- 对象流：字节 `[5, size - shared_mapsize*4)`。
- 尾部：最后 `shared_mapsize * 4` 个字节是共享对象**映射表**：`shared_mapsize` 个 i32 LE 槽位号（marshal.c:489）。`end`——所有载荷读取的上限——被设为该尾部的起点（marshal.c:502），因此**尾部表必须排除在对象流的可读范围之外**；CHECK_SIZE（marshal.c:150-155）会在越过它时报错。

### 长度编码（下文的 "count"）

`READ_LENGTH`（marshal.c:99-108）：一个无符号字节；若它等于 `0xFF`，真实长度随后以**有符号** i32 LE（4 字节）给出。这个位于操作码之前的长度只对 `needlength` 集合中的操作码读取（marshal.c:1221-1224）：TUPLE、DICT、LIST、STRINGL、STRINGR、UNICODE、GLOBAL、STREAM、UTF8、LONG、REF、BLUE、BUFFER。所有其他操作码读取固定大小的载荷（或不读取）。例外：`STRING`（0x10）*不*在 `needlength` 中，它读取自己单独的一字节计数，**没有** 0xFF 转义（marshal.c:643-650）。

### 共享对象机制（清单第 1 项）

- 解码器维护 `shared_obj`，一个含 `shared_mapsize` 个槽位的数组（初始全为 NULL，marshal.c:505-512），外加一个从 0 开始的运行计数器 `shared_count`。
- 对象通过把 `SHARED_FLAG`（0x40）按位或进操作码字节来标记为共享；该标志在分派前被掩掉（marshal.c:524-526）。
- 填充是**存储顺序经尾部表映射**：当第 N 个带共享标志的对象（N = `shared_count`，从 0 起算，按流顺序）被存储时，它落在 `shared_obj[shared_map[N] - 1]`（STORE，marshal.c:111-125）。尾部映射条目把遭遇顺序翻译为槽位；条目会被校验落在 `1..=shared_mapsize` 内（marshal.c:492-499），即**映射条目是从 1 起算的槽位号**。
- 序列/字典/标量类类型在构造时通过 CHECK_SHARED 存储（marshal.c:158-162）：LONG（602）、STREAM/STRINGL/BUFFER（667）、LIST0（714）、DICT（733,739）、GLOBAL（782），而 TUPLE/LIST/DICT 容器在 NEW_SEQUENCE（212）内部的容器*打开*时存储——早于它们的元素解码，这正是循环引用成为可能的原因。
- 延迟容器（DBROW/INSTANCE/NEWOBJ/REDUCE）则在容器打开时*预留*下一个映射槽位（RESERVE_SLOT，marshal.c:128-139, 792），并在对象存在后填充它（UPDATE_SLOT，marshal.c:143-147，位于 907、926、967、997）。因此预留顺序仍然是操作码字节的流遭遇顺序，尽管对象是稍后才构建的。
- 上述列表*之外*的操作码上的 SHARED_FLAG（定长整数、浮点、STRING/STRING1/STRINGR、UNICODE*、UTF8、常量）被参考解码器忽略——不会发生存储。
- `REF`（0x1B，marshal.c:748-764）：载荷是一个计数（READ_LENGTH），用作**从 1 起算**的索引；有效范围 `1..=shared_mapsize`；对象是 `shared_obj[index - 1]`。引用一个尚未填充的槽位是错误（"Shared reference points to invalid object"）。

### 标量

- `INT8`/`INT16`/`INT32`/`INT64`（0x06/0x05/0x04/0x03）：1/2/4/8 字节有符号小端（marshal.c:568-590）。
- `FLOAT`（0x0A）：8 字节 IEEE-754 双精度 LE（marshal.c:606-610）。`FLOAT0`（0x0B）：无载荷，常量 0.0（marshal.c:1244）。
- `MINUSONE`/`ZERO`/`ONE`/`NONE`/`TRUE`/`FALSE` 以及空的 `STRING0`/`TUPLE0`/`UNICODE0`：无载荷；经由 `default:` 分支从常量表（marshal.c:1238-1247）提供。

### LONG（0x2F）——清单第 2 项

marshal.c:592-604。长度 = READ_LENGTH = 载荷的**字节计数**。零字节解码为整数 0。否则为 `_PyLong_FromByteArray(s, length, /*little_endian=*/1, /*is_signed=*/1)`：载荷是**小端二补码**有符号大整数，因此*最后一个*字节的最高位是符号位。遵守 SHARED_FLAG（602 处的 CHECK_SHARED）。

### UNICODE 族（0x12/0x28/0x29）——清单第 3 项

- `UNICODE`（0x12，marshal.c:680-688）：count = READ_LENGTH = **2 字节码单元（字符）数，而非字节数**；载荷是 `count*2` 个字节（CHECK_SIZE(length*2)，第 681 行）的 UCS-2 小端——按 **UTF-16LE** 解码。（参考实现转换为 `wchar_t*`，即在源自 Windows 的数据上是本机 LE UCS-2。）
- `UNICODE0`（0x28）：无载荷，空字符串（常量表，第 1247 行）。
- `UNICODE1`（0x29，marshal.c:670-678）：恰好 2 字节 = 一个 UTF-16LE 码单元；没有计数字节。
- `UTF8`（0x2E，marshal.c:690-694）：count = READ_LENGTH = **字节**计数；载荷是 UTF-8 字节。

### STRINGL 与 STRING 及 BUFFER 的区别——清单第 4 项

三者都产出字节串；差异只在长度编码与共享处理（marshal.c:643-668）：

| 操作码 | 计数编码 | 遵守 SHARED_FLAG？ | 备注 |
|---|---|---|---|
| STRING (0x10) | 自己单独的 0-255 单字节，无 0xFF 转义 | 否 | "deprecated since machoVersion 213"（644） |
| STRINGL (0x0D) | READ_LENGTH（1 字节或 0xFF + i32 LE） | 是 | 已废弃，同上备注（661） |
| BUFFER (0x13) | READ_LENGTH | 是 | "type identifier re-used by CCP. treat as string"（663） |
| STREAM (0x2B) | READ_LENGTH | 是 | 同一解码路径（658-668），见下文 |

STRINGL/BUFFER/STREAM 共用一个 case 主体：读 `count` 个原始字节，完成。另：`STRING0`（0x0E）= 空，`STRING1`（0x0F）= 恰好 1 字节，无计数。

### STRINGR（0x11）——字符串表引用

marshal.c:630-641。Count = READ_LENGTH = **直接**索引进固定全局表；索引 0 被拒绝（`length < 1` → 错误，第 631 行），因此有效索引实际上是**从 1 起算**的（`1..=255`）。表本身*不在* marshal.c 中：它位于 reverence 树的 `src/strings.py`（`stringTable`，256 个条目：索引 0 处的 `None` + 255 个字符串，其中索引 196-255 是 `"#196"`..`"#255"` 占位符），由 `src/blue.py:233` 加载进 `marshal._stringtable`。已逐字提取到 `crates/blue-marshal/src/string_table.rs`（`STRING_TABLE`，256 个条目，索引 0 = `""` 占位符，使线上索引可直接映射）。

### STREAM（0x2B）——清单第 5 项

marshal.c:658-668：帧结构就是 `0x2B` + READ_LENGTH 计数 + `count` 个原始字节。参考实现**不递归**；载荷作为普通字节串返回。按约定，载荷本身是一个完整的 marshal 流（它自己的 `0x7E` 魔数、共享计数、对象数据、尾部映射表），消费方把它喂回 Load——因此嵌套的设置值需要把字节载荷新作为一条流、带自己的共享表进行递归解码。

### 以 `0x7E` 开头的 Bytes 载荷不是嵌套流——任务 9 / 重新测量

这是与上面 `STREAM` 操作码**不同的机制**——两者要分清：`STREAM`（0x2B）是一个专用操作码，其载荷按约定保证是嵌套的 marshal 流（上一节）。下面说的是普通的 `BUFFER`/`STRINGL`（操作码 0x13/0x0D）载荷——解码为普通 `Value::Bytes`，在操作码层面没有任何相应信号——它们只是碰巧以每条 marshal 流开头的同一个 `0x7E` 魔数字节开始。

本节的早期版本声称许多这样的载荷“本身就是完整的 marshal 流”（一种“双重 marshal”模式：一个缓存 blob 存储已序列化的子对象）。该说法**错误**，在此更正。对当前语料的完整重新扫描（`testdata/corpus`，所有快照——历史、新鲜基线，以及后来加入的 exp1–exp5 实验目录——5022 个 `.dat` 文件，解码每个文件并递归遍历完整的 `Value` 树，包括 Dict 的键/值与 Tuple/List/Instance/Stream 子节点）：

- **8739** 个 `Value::Bytes` 载荷以 `0x7E` 字节开头。
- 其中 **0** 个能通过 `blue_marshal::decode` 作为嵌套 marshal 流成功解码。

（最初的任务 9 诊断运行于实验快照存在之前、仅覆盖 1116 个历史 + 新鲜基线文件，在那个较小集合上发现 1942 个此类载荷——结论相同，零个可解码，只是计数发生在语料增长之前。今天对同一 1116 文件子集重跑完全相同的方法仍然精确复现 1942，确认方法是一致的；8739 是完整当前语料的数字。）

所以：以 `0x7E` 开头的 `Bytes` 载荷在真实设置文件中存在，但在观察到的每个语料文件里，没有一个构成有效的嵌套 marshal 流——`0x7E` 是巧合（或来自只是以该字节值开头的数据），不是嵌入式序列化的标记。本语料中没有已确认的“双重 marshal 的设置值”模式；那个描述从未被追溯到 reverence/marshal.c 或任何 CCP 源码，应视为未经验证。

同一次扫描中也没有发现负值 `Long`（见下文 `dump_text` 的 Long 渲染 TODO——因为语料从不触发它而保持未修复）。

**后果：**
- `decode` 刻意**不**尝试自动解码 `Bytes` 载荷：无论它们恰好包含什么，字节都保持精确无损，符合“无有损转换”的约束，并使 `Value::Bytes` 保持单一、可预测的形状。这是正确的，且不受上面更正的影响。
- `dump_text`（value.rs）仍会对任何以 `0x7E` 开头的 `Bytes` 载荷尝试一次 `decode` 调用，成功时渲染 `stream?` + 解码后的值，失败时回退到普通的 `Bytes` 渲染（可打印带引号或十六进制）。鉴于上面的测量，**这个分支在每个真实语料文件上都是死代码**——它的存在纯粹是为 `dump_text` 输出可读性提供的合成数据/面向未来的便利，而不是因为真实设置数据需要它。它有界（`stream_depth < MAX_DEPTH`），所以保留是安全的，但不应依赖或假定它会触发。
- **M1 指南：** 把 `Value::Bytes` 当作不透明字节，就这样。不要围绕“某些 `Bytes` 载荷其实是需要各自重新编码步骤的嵌套 marshal 流”这一假设计划编码器/变异逻辑——语料没有给出该模式存在的证据。

### CHECKSUM（0x1C）——清单第 6 项

marshal.c:613-623。载荷：4 字节 u32 LE = 存储的 adler32 值。不产出对象（`continue`）。实现中的校验（第 615 行）：

    *(uint32_t *)s != (uint32_t)adler32(1, s, end - s)

即 seed = 1（标准 adler32 初始化，vendored `adler32.c`），覆盖范围 = `[s, end)`，其中 `s` 是**那 4 个已存储校验和字节本身**的位置，`end` 是尾部共享映射表的起点。注意自包含：按此写法，被检查的范围*包含*已存储的校验和字节及其之后的所有内容，只排除尾部映射表。这看起来是自引用的；要么 CCP 的写入方计算该值使此式成立，要么该操作码根本不会出现在设置文件中（reverence 还暴露了一个 `skipcrc` Load 标志，marshal.c:1140-1142，表明它通常被绕过）。**M1 编码器指南：不要发出 0x1C**；它是可选的，如果非发不可，先针对真实的客户端写入文件用经验方法核实确切覆盖范围。解码器：读 4 个字节，可选地按参考公式校验，不产出任何东西。

### DICT（0x16）——线上顺序已确认

marshal.c:725-741 + POPULATE_DICT（183-197）+ 内层循环 case（1061-1063）。Count = READ_LENGTH = **条目**数；容器随后消费 `count*2` 个对象。每个条目的线上顺序是**先 value 后 key**（宏注释第 182 行："counted (val,key)"；先到的对象被放进 `obj2`，第二个在 1062 成为字典的键）。空字典（count 0）立即构建。这证实了我们的经验观察。

### TUPLE/LIST（0x14/0x15 + 定长变体）

Count = READ_LENGTH = 元素个数；元素随后按序出现（marshal.c:700-723，在 870-877 填充）。`TUPLE1`/`TUPLE2`/`LIST1` 的隐式计数为 1/2/1，没有计数字节；`TUPLE0`/`LIST0` 为空。NEW_SEQUENCE 在分配前做一次合理性 CHECK_SIZE(count)（202-213）。

### INSTANCE / GLOBAL / NEWOBJ / REDUCE——清单第 7 项

- `GLOBAL`（0x02，marshal.c:766-784）：count = READ_LENGTH，载荷 = `count` 个字节，一个点分名（`module.object` 或内建名），解析为 Python 对象。遵守 SHARED_FLAG。对我们的解码器：保留该名称。
- `INSTANCE`（0x17，marshal.c:787-793 打开；913-944 填充）：没有即时载荷；预留一个共享槽位，随后恰好**两个对象**：(1) 类名（字符串对象；经 find_global 解析，实例创建与共享槽位填充都在状态解码*之前*，917-929），然后 (2) 状态对象，通过 `__setstate__` 或 `__dict__.update` 应用（931-940）。
- `NEWOBJ`（0x23，打开 788-793；填充 947-982）：预留一个槽位，随后一个**元组**，形状为 `(args_tuple[, state])`，其中 `args_tuple[0]` 是类（`cls.__new__(*args_tuple)`，若存在 state 则应用）。之后是一个迭代器尾部：零个或多个作为列表项追加的对象、`MARK`（0x2D）、零个或多个 **key, value** 对（此处 key 在前——"iterated (key,val)"，第 182 行；1057 处的 POPULATE_DICT），由第二个 `MARK` 终止（1014-1058）。
- `REDUCE`（0x22，打开 789-793；填充 985-1010）：帧结构与 NEWOBJ 完全相同，但元组是 `(callable, args_tuple[, state])`，对象是 `callable(*args_tuple)`。同样是 MARK 分隔的先列表后字典的迭代器尾部。
- `MARK`（0x2D，marshal.c:795-798）：无载荷，从不产出对象；只在 NEWOBJ/REDUCE 迭代器尾部内部才有意义。
- `DBROW`（0x2A，打开 786-793；填充 881-910），为完整起见：随后一个对象（一个 DBRowDescriptor，通常经由上述方式构建），然后是一个 READ_LENGTH 前缀的 blob，含打包的（CCP 零压缩）行数据，从流中内联读取，然后是 `descriptor.rd_num_objects` 个尾随的非标量对象。复杂；但愿设置文件避开它。

### GLOBAL 与 INSTANCE——已实现（任务 9）

对照真实语料字节确认（`core_char_123456789.dat` 偏移 0x34c，历史快照）：

- `GLOBAL` 解码为新的 `Value::Global(Vec<u8>)`（与 `Bytes` 保持区分，以便 M1 的编码器可以重新发出操作码 0x02 而不是字符串操作码）。观察到非共享（一个一次性的 callable 名）和带 `SHARED_FLAG`（一个在同文件多个对象间复用的类/callable 名，例如被缓存并 REF 回去的 `__builtin__.set`）两种——后者需要把 `GLOBAL` 加进解码器的 `stores_shared` 集合。
- `INSTANCE` 解码为新的 `Value::Instance { class: Box<Value>, state: Vec<Value> }`。已确认两个子节点是经普通递归路径读取的普通对象（没有 MARK/迭代器帧结构，与 NEWOBJ/REDUCE 不同）：`class` 是类名对象（观察到为 `BUFFER`，其本身带 `SHARED_FLAG`，因为类名跨实例重复——例如 `utillib.KeyVal`），`state` 是 `vec![那一个状态对象]`（观察到为普通 `DICT`，例如 `{"id": "agency", "children": None, "btnType": 1}`）。两个字段都走 `stores_shared` 现有的“子节点之前预留/完成之后存储”路径（与任务 4 中已为容器验证过的相同遭遇顺序机制）——`INSTANCE` 自己的 RESERVE_SLOT/UPDATE_SLOT（marshal.c:128-147）结果不需要除了加入该匹配分支之外的任何特殊处理。
- 语料中没有观察到 `INSTANCE` 使用 `GLOBAL` 编码的类名（按 marshal.c 的 `find_global(obj)`，其中 `obj` 可以是任何字符串类型的对象，总是普通字符串操作码）——单独实现 `INSTANCE`（`GLOBAL` 可用于其 `state` 中嵌套的任何东西）已被独立验证可以关闭所有不含嵌套 `REDUCE` 的语料文件。

### REDUCE——已实现（任务 9）

对照真实语料字节确认（`core_char_123456788.dat` 偏移 0x22，历史快照，以及 `core_user_987654.dat` 偏移 0x684，新鲜快照——两者都经 `__builtin__.set` 重建一个 Python `set`）：

- 解码为与 INSTANCE 相同的 `Value::Instance { class, state }` 形状：`class` 是整个 ctor 对象按解码结果——一个 2 元素 `Tuple`，`(callable, args)`，观察到为 `(Global("__builtin__.set"), Tuple([set 的元素作为 List]))`——因为线上在这里只递给 REDUCE 一个普通对象（元组本身），不像 INSTANCE 那样有两次独立的 class/state 读取。`state` 保存先列表后字典的迭代器尾部贡献的任何东西（见下文）；该字段被复用而不是新增变体，依据任务书的指引——在 INSTANCE/NEWOBJ/REDUCE 之间通用地镜像加载顺序。
- callable 观察到既有普通 `GLOBAL`（非共享）也有 `GLOBAL|SHARED_FLAG`（在同文件多个 REDUCE 出现处缓存）——两者都由 ctor 的通用递归解码处理，即元组的第一个元素，不需要 REDUCE 专用代码。
- 先列表后字典的迭代器尾部（marshal.c 在构建对象之后无条件切换到 `LIST_ITERATOR` 再 `DICT_ITERATOR`，985-1011/1014-1058）在线上**总是存在**——语料中观察到的每个 REDUCE 之后都紧跟两个连续的 `MARK`（0x2D）字节，中间没有任何东西，即一个空尾部。解码器实现的是一般的 MARK 终止循环（而不只是“期望紧跟着两个 MARK”），因为那是 marshal.c 规定的实际强制帧结构，不是推测性扩展：它把对象读进 `state` 直到一个 MARK，然后把 `(key, value)` 对（注意：*迭代*顺序是 key 在前 value 在后，与普通 DICT 计数的 value 在前 key 在后相反，依据 marshal.c:182 的 POPULATE_DICT 宏注释）作为 2 元素 `Tuple` 读进 `state` 直到第二个 MARK。非空尾部只由一个合成单元测试（`decodes_reduce_with_nonempty_iterator_tail`）演练，语料从不演练。
- `NEWOBJ`（0x23）共享完全相同的帧结构（用 `(args_tuple[, state])` 而不是 `(callable, args_tuple[, state])`，依据 marshal.c:947-982）。语料中从未出现，但一个 2026-09 的角色文件带有一个——`trackedSkillPlanID` 下的一个 `uuid.UUID`，`NEWOBJ TUPLE2(TUPLE1(GLOBAL "uuid.UUID"), DICT{"int": LONG<16 bytes>}) MARK MARK`——所以它现在经同一循环解码为 `Value::Reduce { newobj: true, .. }` 并重新编码为 0x23。`DBROW`（0x2A）仍保持 `Unsupported`；它从未出现过。

## 语料规范性测量（2026-07-13，M1a）

在编码器设计之前，对全部 5022 个语料文件跑了一遍带插桩的解码器（0 个解码失败）；这些事实支撑了编码器的规范操作码规则以及 `Value` 上的保真度标签。逐字节相同的往返门禁（tests/corpus.rs）每次运行都会重新证明所有这些事实，因此未来某个客户端补丁若破坏了其中一条，会在这里大声失败。

| 测量项 | 计数 |
|---|---|
| READ_LENGTH 0xFF 转义 / 其中非最简（< 255） | 228,549 / **0** |
| 根对象与尾部映射表之间有空隙的流 | **0** |
| 槽位 ≠ 遭遇序号+1 的尾部映射条目 | **963,660** |

| n ≤ 2 的计数 TUPLE / n ≤ 1 的计数 LIST | **0** / **0** |

| 0 载荷字节的 LONG | **0** |

| STRINGR 操作码 | 71,847 |
| 内容与表条目相同的非 STRINGR 字符串 | 1,269 |

编码器后果：

- **规范（无需标签）：** 长度编码永远最简；`Int` 按大小（先常量，然后最窄的 INTn）；`Float` +0.0 位型 → FLOAT0；`Bytes` 按长度（STRING0/STRING1/BUFFER）；`Tuple`/`List` 按计数。
- **带标签（内容无法还原操作码）：** `Str`（UTF8）vs `StrUcs2`（UNICODE0/UNICODE1/UNICODE 按 UTF-16 单元数）vs `StrTable`（STRINGR 索引）——客户端既发出 UTF8("") 也发出 UNICODE0，且把表内容字符串也写成 UTF8（1,269 处冲突），所以“到表里查”会编码错误。
- **显式共享：** 尾部映射表严重非恒等，因此解码后的树带有 `Shared { slot }` 包装器和 `Ref(slot)` 节点；编码器按遭遇顺序重放槽位。SHARED_FLAG 永远不在非存储操作码上发出（在那里也从未观察到）。
- **空隙升级为硬错误：** `ErrorKind::TrailingBytes`——测量为零次出现，因此任何空隙现在都意味着解析错误。

## 映射

下面所有路径都是从文件根开始的字典键序列（每个 `core_char_*.dat` 的根都解码为一个 Dict）。通过对单次游戏内改动前后的 dump 做 diff 确立（任务 10 实验）。

### 值包装约定（适用于全文件）

大多数叶子设置以 2 元组 `(timestamp, value)` 存储，其中 `timestamp` 是一个 LONG，保存一个 Windows FILETIME（自 1601-01-01 UTC 起的 100 纳秒 tick 数）。客户端每次保存都会为许多条目重写这些时间戳，因此时间戳变动是同一文件两次保存之间主要的 diff 噪声。编辑器必须保留包装器（编辑时重写时间戳正是客户端自己做的；保留旧的看起来也无害——尚未验证）。

### 窗口几何（实验 1–2：移动，然后缩放总览窗口）

- 文件：`core_char_<id>.dat`（角色作用域；配对的 `core_user` 文件在该会话中也被重写过，但不含几何信息）。
- 路径：根 → `b"windows"` → `b"windowSizesAndPositions_1"` → `(timestamp, dict)`；内层字典把窗口 id 映射到 6 元组 `(x, y, width, height, screenW, screenH)`，全部是绝对像素（观察到：在 2560×1440 客户端上总览为 `(2114, 424, 446, 1016, 2560, 1440)`；垂直移动窗口只改变了元素 1（y）：0 → 424）。
- 缩放确认（实验 2）：缩放把元组改为 `(1707, 288, 853, 1152, 2560, 1440)`——w/h 是元素 2–3；x/y 也移动了，因为拖拽起点移动了。除时间戳变动外，这个元组是文件中*唯一*的变化，因此几何在这里完全自包含（别处没有影子副本）。
- `screenW`/`screenH` 是几何保存时的客户端分辨率，按窗口内嵌——这是布局画布的分辨率来源（规范 §6）；不需要单独的全局分辨率键。
- 窗口 id：单例窗口用普通字节串（`b"overview"`、第二个总览窗口用 `b"overview_1"`、`b"fitting"`、……），参数化窗口用字符串化的 Python 元组（Str，例如 `"('corpassets', 1000000000001L)"`）。两类都作为同一字典的键出现。
- 跨窗口通用（实验 5）：移动市场窗口只改变了同一 `windowSizesAndPositions_1` 字典中它自己的 6 元组（x/y `(1544, 55)` → `(16, 825)`）以及它的 `b"openWindows"` 标志——每个窗口都用同样的结构，因此布局画布可以通用地枚举这个字典；没有按窗口的特殊情形。
- 存储的窗口标志位于根 → `b"windows"` 下的兄弟条目 `(timestamp, 按窗口 id 的字典)` 中：`b"openWindows"`、`b"collapsedWindows"`、`b"minimizedWindows"`、`b"lockedWindows"`、`b"compactWindows"`、`b"isOverlayedWindows"`、`b"isLightBackgroundWindows"`、`b"stacksWindows"`，以及 `b"pinnedWindows"`（值为 bool，stacksWindows 除外：栈 id）。`pinnedWindows` 在 2026-07-22 与 2026-07-12 两个语料快照的 384 个角色文件中都有 352 个存在——是一个稳定的键，不是正在逐步引入或淘汰的键。这些就是规范中的 WindowLayout 标志字段。
- **`openWindows` 是还原列表，不是可见性标志**（2026-07-26 对照该角色运行中客户端的截图测量得出）。它是累积的：EVE 记录它会还原哪些窗口，并且从不可靠地清除条目。一个真实角色文件持有 **381 个窗口，134 个被标记为打开，83 个画布绘制单元，而实际上屏幕上有约 9 个窗口**——打开集合包括 `setQuantityPopup`、`enterShipPassword`、`ship_name_dialog`、`kickCharacterFromChat` 和 `DisconnectNotice` 之类的一次性模态框。**没有其他存储信号能把可见的与仅仅打开的分开：**`minimizedWindows` 对 1 个窗口为 true，`collapsedWindows` 对 0 个；134 个中只有 14 个是在过时分辨率下保存的；它们之中有 82 个不同的矩形，因此不存在可作为依据的“从未定位过”的默认位置聚类。最接近的关联信号是在 `compactWindows` 中*有一个条目*（10 个窗口，其中 8 个可见），但它记录的是“用户在该窗口上切换了紧凑模式”，而不是可见性——而且它漏掉了在屏幕上的 `directionalScannerWindow`。对任何编辑器的后果：布局画布只能显示 EVE 会还原的东西，而要分离出瞬态窗口需要一份人工整理的清单，这本质上是不完整的。
- 总览列*宽度*观察于根 → `b"ui"` → `b"SortHeadersSizes"` / `b"SortHeadersSettings2"`，以元组 `(b"overviewScroll2", presetIndex)` 为键 → 列名 → 宽度像素的字典（细节待实验 3 确认）。

### `openWindows` 不能预测客户端启动时显示什么

**2026-07-31** 对一个真实角色文件（`core_char_96000002`，Pilot Echo）确立，起因是一份报告：编辑器显示 Job Board、Contracts、Corporation 和 Structure Browser 为打开，而游戏内没有一个可见。

**有一类窗口无论 `openWindows` 怎么说，客户端在启动时都从不还原。** 该标志没有损坏，编辑器读取它也正确——客户端只是对这些窗口不 consult 它。`openWindows[id]` 记录的是该窗口在某次持久化时是打开的，而对这一类窗口来说，这与游戏启动时出现什么无关。

证据，全部来自真实文件：

- **互斥的对话框全部同时被标记为打开。** 381 个窗口中有 134 个读为打开，其中包括 `ship_name_dialog`、`skill_requirement_dialog`、`contractSelectItemTypeDlg`、`AddToBlockSearch`、`newMessageReceiverSearch`、`createcontract` 和 `contractdetails`。这些是一次只能开一个的模态框；玩家不可能在跃迁时同时打开七个。
- **该标志跨会话粘滞。** 被报告的四个窗口在同一角色 2025 年 4 月的副本中读为 `false`，到 2026-07-27 翻转为 `true`，在 2026-07-31 的写入中仍是 `true`——那次写入是客户端在截图显示那些窗口不存在之后一分钟内做出的。所以文件是新鲜的，标志就是错的，而不是文件过时。
- **干净的客户端关闭不清除它。** 直接测试过：在游戏内打开 `corporation`，然后退出客户端，客户端重写了文件（20:05:50 → 20:20:49）。*打开集合里没有任何东西变动*——仍是 381 中的 134，`job_board`、`contracts` 和 `StructureBrowser`——都没有被打开过——仍为 `true`，上面每个模态框也仍为 `true`。这排除了“客户端只在退出时持久化、而文件是会话中途的”这种解释，因为退出时的那次写入本身就把肯定没打开的窗口报告为打开。
- **决定性的证据：客户端在启动时忽略该标志，但完美跟踪该窗口的几何。** 那次关闭之后重启客户端，`corporation` 是*关闭*状态出现的，尽管它的 `openWindows` 读为 `true`。移动它并重新打开，然后再次退出，重写了文件（20:20:49 → 20:24:26），**记录了新位置——`753,90` → `603,65`，大小不变**——而打开集合完全没有变动：仍是 381 中的 134，每个 id 和其他每个几何值都一模一样。

  这一对就确定了机制。客户端显然在跟踪这个窗口并持久化它学到的东西，因此该标志不只是没人维护的过时数据。它写入 `open=true`，然后在启动时拒绝据此行动。所以有用的陈述不是“标志是错的”，而是“标志不是决定你是否看到该窗口的东西”。
- **文件里没有别的东西跟踪可见性。** `windows` 段有 18 个键；`minimizedWindows`、`collapsedWindows` 和几何对这些窗口全部读为“normal”，编辑器已经投影了每一个相关的。没有更好的信号可切换。

**该标志能带回哪些窗口——2026-10-11 从客户端代码读出。** 恰好一个模块读取 `openWindows`：`eve/client/script/ui/services/sessionChangeWindowOpener.py`，在每次会话变更时，针对一个固定的类列表（`_TryOpenWnd` → `GetRegisteredState(id, 'open')`）：

- 总是：`mail`、`walletWindow`、`assets`、`XmppChatChannels`、`journal`、`logger`、`charactersheet`、`addressbook`、`locations`、`market`、`notepad`、`standaloneBookmarkWnd`；
- 停靠在空间站：空间站库存（`InventoryPrimary` 以及物品、舰船、发货和军团仓库窗口）；
- 停靠在建筑：建筑库存、发货和军团仓库；
- 在太空：`InventoryPrimary`、`MoonScanner`、`directionalScannerWindow`、`probeScannerWindow`，以及星系地图面板（每个只在未嵌入扫描器或在该星系被抑制时）。

其他每个窗口的标志都从不被 consult。像总览、Selected Item、无人机和聊天这样的窗口由它们自己的服务打开，无论该标志如何；`corporation`、`job_board`、`contracts`、`StructureBrowser` 以及上面的模态框就是从不重新打开——这正是 2026-07-31 的观察。所以从不还原的一类是“不在此列表上、也不由服务打开的所有东西”，而该列表是可推导的而非人工整理的。由服务打开的集合：在太空 `tactical` 打开每个总览窗口、`selecteditemview` 和 `droneview`；停靠时 `dockedUI` 打开 `lobbyWnd`；聊天服务打开已加入的频道。`fleetwindow` 和 `watchlistpanel` 只在舰队操作时打开。两个列表都在 `app/src/lib/data/window-filters.json` 中作为 `restored` 和 `service_opened`，编辑器把其他所有窗口视为关闭（2026-10-11）。

**对编辑器的后果。** `WindowRect.open` 是 EVE 的标志，也只能是 EVE 的标志。画布绘制打开的窗口，因此其中某个会为一个客户端不会显示的窗口画出矩形。实践中两样东西吸收了它：人工整理的杂乱表已经覆盖了瞬态对话框（`windowLabels.ts` 中的 `CLUTTER_IDS` 包含上面列出的每一个），而按窗口的“Treat as clutter”覆盖处理其余的——这正是 `job_board` 这样的普通窗口所需要的，因为它确实是玩家放置的窗口，绝不能被表归类为杂乱。

`windowLabels.ts` 已经在注释中记录了该机制；本节是其背后的证据，也是 `Open only` 筛选带有一条如此说明的 tooltip 的原因。

### 窗口栈（实验 6：把两个自由窗口标签页化进一个新栈）

在游戏内把两个自由浮动窗口标签页化到一起会创建一个**新栈**，其容器是一个*铸造出的数字字符串窗口 id*，它本身是一个真实定位的窗口。已由一个角色文件的前后 diff 确认（下面为合成 id：两个被标签化的窗口 `windowA`、`windowB`；铸造出的容器 `N`）。EVE 填入了一个**空闲**整数 id——观察到的 id 是其他活跃数字 id *下方*的一个空洞，因此这是空闲列表挑选，不是 `max+1`。

根 → `b"windows"` 下的完整变更集（除时间戳变动外）——编辑器铸造一个栈所需的完整配方：

- `b"windowSizesAndPositions_1"`：**三者共享一个完全相同的矩形**——新条目 `N → (x, y, w, h, screenW, screenH)`，`windowA`/`windowB` 被重写为同一个 6 元组（成员原先的自由浮动矩形被丢弃）。容器的矩形就是栈的真实屏幕位置。
- `b"stacksWindows"`：`windowA → N`，`windowB → N`（成员 → 容器；先前未入栈的成员其值从 `None → N`）。
- `b"preferredIdxInStack3"`：新条目 `N → { windowA: 0, windowB: 1 }`（容器 → {成员 → 从 0 起算的标签页索引}；标签页顺序）。
- `b"openWindows"`：`N → True`，两个成员都被强制 `→ True`。
- 容器在三个布尔状态字典中被标记为真实窗口，每个都是 `N → False`：`b"isLightBackgroundWindows"`、`b"isOverlayedWindows"`、`b"minimizedWindows"`。（成员若原先在 `b"isOverlayedWindows"` 中没有条目，也可能获得一个 `False` 条目。）容器**不**需要在 `b"collapsedWindows"` / `b"compactWindows"` / `b"lockedWindows"` 中有条目。

具名框架的栈（`b"ChatWindowStack"`、`b"invitestack"`）与其他铸造出的数字容器（如 `b"76"`、`b"448"` 这样的 id）在真实文件中已经共存，各有自己的几何 + 标志——数字字符串容器是正常的，不是特殊的。栈的值是窗口 id 引用或 `None`，**绝不是 Int**，因此 `windows.rs::stack_field` 的仅 Int 检查在真实数据上是死代码。

**编辑器含义（window-stacks 里程碑）：** 铸造一个栈是机械性的，上面已完整规定；容器 id 只需*在文件中空闲*（空闲 id 集合可从这些字典枚举），因为客户端在加载时会跟踪活跃窗口 id，不会回收它看到正在使用的。一个残留的未知——是否存在某个 next-window-id 计数器持久化在 `b"windows"` *之外*——这次单次抓取无法解决；防御性地选一个高位空闲 id，并在该功能的真实冒烟测试中确认无冲突。

**被删除的框架保持删除。** 2026-07-28 已验证：两个孤立的栈框架（`43`、`51`）从一个真实角色文件中被移除，客户端跑过完整登录/登出，两者都没有回来——而同一文件中六个未触碰的对照项原样未动。因此孤立框架可以直接安全删除；客户端既不还原它，也不把它的缺失当作损坏。

**栈从不保留一个窗口。** 2026-10-10 从客户端代码读出（`WindowStack.RemoveWnd`，carbonui/window/stack.py）：当一个窗口离开栈、只剩一个时，客户端把那一个也移除——放置在栈原先所在的位置，其 `stacksWindows` 条目与首选索引被清空——并关闭空的栈。唯一的例外是折叠的栈，它保留其最后一个窗口。被关闭框架的几何不会被删除，孤立框架就是这样累积起来的。加载不会修复只有一个成员的栈（`Check` 只关闭没有窗口的栈），因此编辑器在拖出动作本身上执行解散（`stacks::unstack`）。

### 我们的 pack 导出 vs EVE 自己的

2026-07-28 比较（真实计划项 28、29、31）：通过编辑器导出一个账号的总览，把该文件喂给 EVE 自己的 Overview Settings 导入器，再从客户端导出一次。

- **EVE 接受我们的导出。** 客户端导入了它，预设按名称回来了。这就是项 27。
- **标签页顺序精确存活**——全部八个标签页，相同顺序，两个文件都是（项 31）。
- **`applyToShips` 不在任何一个文件中。**（原文为 applyOnlyToShips）它也不出现在任何已发布的 pack 中，这证实了 `overview_pack.rs` 的备注——在当前客户端上它是一个没有对应键的 pack 名（项 29）。没有可映射的东西。
- **两个导出互不为超集**，所以不要指望字节匹配：
  - *格式化。* 我们写块样式并给标量加引号（`-` 单独一行，`- 'ICON'`）；EVE 写紧凑裸样式（`- - background_13`、`- ICON`）。相同内容在我们这边行数是 1.5–2 倍，这就是我们的 `presets` 段 10,544 行对 EVE 的 5,645 行的全部解释——不是数据丢失。
  - *EVE 把文件中隐式的东西实体化。* 它的导出在 `stateBlinks` 下列出四个 `flag_*` 条目，而这些**根本不在账号文件中**（账号文件只含两个 `background_*`，没有 flag 条目）。我们的只发出存储的东西。
  - *EVE 完全丢弃 `userSettings`*——它发出 `userSettings: []`，而我们携带文件真正持有的五个布尔值（`applyToStructures`、`applyToOtherObjects`、`useSmallColorTags`、`useSmallText`、`overviewBroadcastsToTop`）。

  注意这与下面的标志面规则相抵触：EVE **保留** `flag_*` 闪烁但**丢弃** `flag_*` 颜色。相同的键形状，不同的对待。

**EVE 自己的导入器会删除 `tabsByWindowInstanceID`。** 账号 A 在每次离线暂存（`baseline` … `staged-7`）中都带着该键，而在紧接着的下一次抓取中它消失了——那次抓取发生在把一个 pack 喂给客户端自己的 Overview Settings → Import 的会话之后。该账号此后一直持有 `tabsettings_new` 而没有窗口映射，其总览在游戏中仍然工作。

两个值得记住的后果：

- 它解释了为什么 pack 格式没有为按窗口的标签页映射提供表示——客户端丢弃它自己的。我们的导出和 EVE 的导出都不携带该键（两边都是 0 次出现）。
- **“无窗口账号”不是罕见状态。** 客户端自己在一次普通的游戏内 pack 导入中就把账号置于该状态，因此任何通过 EVE 导入 pack 然后打开我们总览编辑器的用户都处于该状态。`overview.rs::window_groups` 返回空 vec，`add_overview_window` 以 `NoWindowMapping` 拒绝——这读起来曾经像一个针对损坏文件的边界情况，2026-07-28 被改写为描述一种配置。关于写回该键所遵循的规则，见下文“真实账号上的 `tabsByWindowInstanceID` 形状”。

**比较的注意事项。** 这两个文件不是干净的往返对：在我们的导出与客户端的导出之间，通过编辑器导入过一个社区 pack，因此差异不能确定地归因于 EVE 的归一化。上面三点是安全的，因为每一点都是类别差异（样式、整段的存在与否、文件中完全缺失的值），而不是可能漂移的值。一次严格的往返——导出、经 EVE 导入、再导出，中间什么都不做——如果确切的归一化将来变得重要，仍然值得一整个会话去做。

### 铸造零时间戳是安全的

凭空创建一个容器键意味着发明它的 `(timestamp, payload)` 包装器，而本代码库中每条这样的路径都铸造 `Value::Long(vec![0u8; 8])`——一个零，而 EVE 写入的每个键都持有真实 FILETIME（`134295…`）。**2026-07-27 在游戏内确认无害**：账号 B 带着 `tabsettings_new` 和 `tabsByWindowInstanceID` 都为 `0L` 进入客户端，客户端读取了它们、使用了它们，并在退出时盖上自己的时间戳（`134296537985022289L`、`134296538635206714L`）。那个零再也没出现过。

同一次抓取还显示 **EVE 容忍并保留空的总览窗口**：账号 B 的 `tabsByWindowInstanceID` 在一个 5 标签页的 pack 落到一个 4 窗口的账号上之后是 `[[0,1,2,3,4],[],[],[]]`，从客户端回来时原样未变，而不是被修剪。

### HUD 锚点

**放置约定 2026-07-27 在游戏内确认**（A1，2560×1440，UI 缩放 1.0），依据真实验证计划 §4 的两点抓取法：写一个已知值，观察客户端把它画在哪里，把它拖到别处，把值读回来。一次读数无法区分原点与符号；两次可以。

- **`shipuialignleftoffset` 是相对中心的，负值向左。** 写入 `0.0`，舰船 HUD 水平渲染在*正中央*——这也排除了左边缘原点，因为那样会把 `0` 放到 neocom 上。向左拖动，客户端回写 **`-642.0`**。因为 `0` 使它居中，该偏移移动的是**中心**，不是左边缘：在 2560 宽的屏幕上，`-642.0` 把那个点放在 638。A1 原有的 `-189.0` 读作“中心左侧 189px”。是*哪个*中心由 2026-07-28 的测量确定——是电容器轮的中心，不是元素的；见下文。
- **`fightersDetachedPosition` 是面板的左上角，绝对屏幕像素，原点在屏幕左上角。** 2026-07-28 通过写入 `(839, 497)`——497 正是该角色 D-Scan 窗口的精确上边缘——并把两者一起拍照确定：战斗机面板的能力网格与 D-Scan 顶部齐平绘制，客户端把这对值原样回写。更早的一次抓取似乎显示 y 位移了约 234px。它错了两次，两个陷阱都值得任何未来在此处的锚点工作了解：它来自一次拖到**角落的拖动，而角落会钳制**，而且战斗机面板的*可见*范围随战斗机能力网格是否绘制而变化——没有战斗机升空时，只显示小队那一行，而那一行位于面板锚点下方约 150px 处。锚点是能力网格的起点，无论它是否被绘制，这正是它稳定的原因。要对照屏幕上已知的参考测量，永远不要对照角落。
- **`notification_badge_offset`** 是一个 32x32 小部件的左上角，绝对屏幕像素，钳制到屏幕内；缺失时，客户端把它放在 **(16, 16)**。2026-10-11 从客户端代码确定（`notificationCenter.LoadPositionValues` / `capWidgetPosition`，`notificationSettingHandler.GetNotificationBadgeOffset`）。

**`shipuialignleftoffset` 锚定的是电容器轮，不是元素的方框。** 2026-07-28 从三张原生 2560×1440 截图测量（Pilot Golf，配置档 `d_games_eve_sharedcache_tq_tranquility`，文件在截图之后写入，使锚点与像素匹配；`shipuialignleftoffset = -642.0`）。

通过颜色隔离出电容器轮，其中心在 **x = 638.5**，与文件算出的 `2560/2 + (-642) = 638` 相符。该元素关于该点强烈**不对称**：它向**左延伸 148px**，向**右延伸 495px**，在最宽（8 槽）模块行处跨越 490..1133。

同一角色在同一偏移下的两张截图，分别驾驶战列舰和护卫舰，共享一个逐像素相同的左边缘（490），只在右侧不同（1133 vs 896）——装备架从固定左边缘向右生长。这也是为什么 2026-07-27 的实验看到偏移 0.0 把 HUD 画在“正中央”：居中的是电容器，不是方框。

垂直范围，顶对齐：**y 28..187**（高度 160）。

**在第二个偏移上确认，且边距不对称（会话 C，2026-07-28）。** 拖动 HUD 使客户端写入 `-1052`，在上面 `-642` 左边 410px。在该偏移下，电容器轮中心测得 **228.0**，与 `2560/2 + (-1052) = 228` 相符——精确。左侧舰船控制按钮列移动了完全相同的增量（`(490,512)` → `(80,102)`），因此它属于 HUD，148px 的左延伸是测得的，不是推断的。

同一会话首次捕获了 HUD **底对齐**（`shipuialigntop` 为 false）。模块装备架块在两种对齐下都是 127px 高，位于元素内 4px 处，顶对齐时在 y 32，底对齐时在 y 1272——因此底对齐时元素跨越 **1268..1428**，其下方间隙为 **12px**，而不是上面的 28px。该元素在垂直方向并不对称，而镜像上边距（编辑器在此之前一直这么做）会把方框画高 16px。

**缺失时，`fightersDetachedPosition` 为 `(W/2, H/2 − 60)`**，针对客户端运行所用的屏幕（`shipUI.GetFightersDetachedPos`），并且客户端把存储的点钳制到 `x ≤ W − 32`、`y ≤ H − panel height`（`shipUI.UpdatePosition`）。2026-10-11 从客户端代码读出。

**`fightersDetachedPosition` 是面板的左边缘与能力网格的顶部**——2026-07-28 再次确认：存储的 `(329, 289)` 对照测得的左边缘 ≈333 和网格顶部 289。4 个中队（3 个已发射）时面板跨度 **381×253**；列间距为 **86**，能力网格与中队行共用，因此 5 中队航母的最大宽度为 **467**。高度与中队数量无关。

**两个元素的内部几何**，同一天测量并记录，供未来的绘制层使用（编辑器今天只画普通矩形）。所有偏移都是从元素自己的左上角起算：

| 元素 | 部件 | 相对方框原点的偏移 | 间距 | 数量 |
|---|---|---|---|---|
| 舰船 HUD | 电容器轮中心 | x 148（= 锚点），y ~74 | — | 1 |
| 舰船 HUD | 电容器环外缘 | 跨越 x 73..231（⌀ ~158） | — | 1 |
| 舰船 HUD | 模块槽位行 | 首个槽位 x 245，各行顶部 y ~2 / ~50 / ~94 | x 50，y ~46 | 8 × 3 最多 |
| 战斗机 | 能力网格 | x 70，y 0 | 86 | 5 × 3 最多 |
| 战斗机 | 中队行 | x 43，y ~178 | 86 | 5 最多 |

槽位与中队间距在两张舰船截图间稳定，因此装备架宽度为 `245 + 50 × slots`（从方框原点起算）——8 槽最大值由此得出 643 的总宽度。

EVE 在哪里存储布局画布绘制的屏幕构件——舰船 HUD（电容器加装备架）、分离的战斗机 UI、neocom 和通知徽章。下面每个键都是普通的 `(timestamp, value)` 叶子节点，因此需要常规的值包装器解包。计数是 2026-07-22 语料快照（384 个角色文件，175 个账号文件）中包含该键的文件数。

角色文件（`core_char_<id>.dat`）：

- 根 → `b"windows"` → `b"shipuialignleftoffset"`：Float，例如 `-189.0`、`-173.0`——舰船 HUD 的水平偏移。315/384。布局面上唯一的浮点，这对写入路径有影响（`NewValue::Float`）。
- 根 → `b"ui"` → `b"fightersDetachedPosition"`：Int 2 元组，例如 `(326, 54)`。319/384。
- 根 → `b"notifications"` → `b"notification_badge_offset"`：Int 2 元组，例如 `(2519, 131)`。313/384。**注意段名**：这是唯一*不*位于 `ui` 下的 HUD 锚点，`ui → notification_badge_offset` 在任何语料文件中都不存在。这些笔记和 `hud.rs` 在 HUD 切片尚在草稿时都写了 `ui`——在 v0.15.0 发布前被发现，现在由 `tests/hud_corpus.rs` 守护，这是手工构建的测试夹具无法发现的。

账号文件（`core_user_<id>.dat`）——这些是账号级的，因此一次编辑会改变该账号上的每个角色：

- 根 → `b"ui"` → `b"shipuialigntop"`（Bool，131/175）、`b"detachFighterUI"`（Bool，130/175）、`b"displayFighterUI"`（Bool，131/175）、`b"showSensorOverlay"`（Bool，罗盘——重塑舰船 HUD；见“舰船 HUD 内部结构”）。
- 根 → `b"windows"` → `b"neocomWidth"`（Int，例如 `37`，130/175）——**遗留，从不读取。** 2026-10-11 从客户端代码更正：宽度是一个角色设置（`neocomSettings.neocom_width_setting`，一个 `CharSettingNumeric` → `settings.char.ui`，默认 **48**，钳制 32..72）。账号文件整个 `windows` 段是迁移前的存储：`carbonui.window.settings.migrate_window_settings_from_user_to_char` 把它一次性复制进角色文件（标记 `__usercopy__`），之后再也不读它。在机主的机器上，账号键读为 37，写于 2022 年，而角色的 `ui → neocomWidth` 读为 72。客户端只在栏被调整大小之后才写角色键，因此大多数角色文件没有它，绘制默认的 48——这正是每次抓取中 48px 栏所显示的。

**账号文件的 `ui` 段键是 `Ref` 键控的**——一个 `Ref`，其字节串定义在流中*更晚*出现，尾部共享对象表使这合法。因此比较裸 `Value::Bytes` 的段查找（如 `treewalk::is_bytes` 所做）会完全错过它，从真实账号文件中投影不出任何东西；先通过 `effective` 解析段键。`hud.rs::section` 就是这么做的。

缺失意味着“EVE 的内建默认值”，不是“零”：69/384 个角色文件根本没有 `shipuialignleftoffset`。铸造一个 `(Long(0), value)`——零时间戳铸造已被总览预设容器证明——就是 `hud.rs::set_hud_value` 所做的。

**两种锚点约定现已在游戏内确认**（2026-07-27/28）——抓取细节见上文“HUD 锚点”一节。两个猜测都对了：

- `shipuialignleftoffset` 是**相对中心的**，正值向右，锚定的是**电容器轮的**中心——不是元素自己的中心，上面 2026-07-28 的测量把两者区分开了。最初的依据（两个不同宽度客户端上的小负值）是站得住的。
- 两个点元组是绝对客户端像素中的**左上角**。曾让本笔记担心的反例——一个角色在 2560×1440 客户端上读为 `(1280, 660)`，x 正好是屏幕宽度的一半——是巧合，不是中心锚点。

**屏幕上的尺寸已测得**，截至 2026-07-28（舰船 HUD 643×160，战斗机 UI 467×253）——见上面的占地测量。两次真实会话都未能测出：舰船 HUD 没有可对齐的硬边缘，战斗机面板的范围随其能力网格是否绘制而变化；截图把两者都定了下来。旧的发明值（686×250 和 400×120）偏小，而且对舰船 HUD 还锚错了。**徽章的 32×32** 是客户端自己的小部件尺寸（`notificationCenter.widgetWidth`/`widgetHeight`），2026-10-11 从其代码确认。

更正其中任何一个都是 `layout.ts` 的 `HUD_NOMINAL` 中的一处编辑，加上配对的放置/逆变换对（`hudRects` ↔ `shipOffsetFromX` 和 `hudRects` ↔ `hudPointFromRect`），往返单元测试会把它们钉在一起。

### 舰船 HUD 内部结构

**2026-07-30** 为画布细节层测量，取自 2026-07-28 那一轮所用的同样两张原生 2560×1440 截图（`hud_battleship.png`、`hud_frigate.png`，偏移 −642，顶对齐）——但依据**行/列亮度剖面而非目测**，这正是使其可复现的原因。偏移从元素自己的左上角起算，即 `HUD_NOMINAL.shipui` 描述的方框。

同一偏移下的两艘船在下面每个数字上都一致。正是这一点把元素的结构与某一艘船的装配区分开。

| 部件 | 几何 |
|---|---|
| 舰船控制簇 | x 0 和 30 两列，按钮 ⌀30，垂直间距 32；A 列从 y 24 起 4 个按钮，B 列**从 y 40 起 3 个按钮**（低半步） |
| 电容器 | 居中 (148, 72)；外缘 r 80，量表带 r 50..80 **仅上半部**，内环 r 42，发光核心 r 27 |
| 模块装备架 | 圆形按钮 ⌀44，从 x 247 起列间距 51，各行从 y 4 起统一 44 间距 |
| 装备架错位 | **中间行偏移 +25**，半个间距，且少一个按钮 |

**所有这些都是在传感器覆盖罗盘开启的状态下测量的**，客户端代码显示它会改变形状（2026-10-11）。账号 `ui → showSensorOverlay`（Bool，除非存储否则关闭——`shipUI.is_compass_enabled`）把模块装备架再向右移 16px（`slotsContLeft`：`SLOTS_CONTAINER_LEFT + 16 − 8`），把左侧按钮簇再向左移 10px（`hudButtonsLeft` 690 对 680）。测得的数字与罗盘开启的代码逐像素相符：装备架在电容器 + 99 处，簇从电容器 − 150 起。没有罗盘时方框宽 **622**，电容器在 **138** 处。姿态与采矿扫描器按钮（取决于舰船，不在任何文件中）把装备架再向右推 32px。代码还确认了网格本身：列间距 `int(32 × 1.6)` = 51，行间距 `int(32 × 1.4)` = 44，中间行偏移半个列，每行 8 个槽位。

这纠正了三件事，每一件都曾让绘制出的 HUD 出错：

- **按钮是圆的，不是方的。** 模块槽位与舰船控制按钮都是。细节层在此之前一直画 44×40 的矩形。
- **中间装备架行是错位的。** 护卫舰：中行在 762/813/864，外行在 737/788/839。战列舰：813/915/966 对 788/890/941。两者都恰好 +25。这种砖砌图案是装备架的视觉签名。
- **舰船控制簇属于 HUD，而此前完全没有被绘制**，使方框左三分之一空着。2026-07-28 已记录它恰好按 HUD 的拖动增量移动——148px 的左延伸就是这样确立的——但从来没人绘制它。

对早先数字的两处更正，都来自测量而非推导：

- **列间距是 51 而非 50，首列在 247 而非 245**，因此 8 槽行的右边缘是 `247 + 51 × 7 + 44 = 648`，不是 643。`HUD_NOMINAL.shipui.w` 原为 643——按 `245 + 50 × 8` 推导，把间距和按钮宽度混在一起——所以方框窄了 5px，窗口会吸附到真实 HUD 紧内侧。更正为 648。
- **各行顶部是 4 / 48 / 92，统一 44 间距**，不是上面记录的 2 / 50 / 94，后者给出不均匀的 48 然后 44。

#### 垂直范围，重新测量——而且边距其实是相等的

电容器的外缘达到 **r 88**，这就是元素的全部高度：圆盘恰好从上到下填满方框。

走到这一步经历了两次值得记录的更正，因为两个都是陷阱：

1. 全圆亮度扫描在 **r 80–81** 处急剧达到峰值。那是外缘明亮的*中部*，不是它的边缘。在 12 点方向的 5 倍裁剪显示暗的外缘弧及其高光段一直向外延伸到 **r 88**，在量表刻度开始之处之上。把扫描峰值当作边缘会使元素顶部低 8px。
2. 电容器下方是小的彩色无人机状态指示器。它们是**舰船状态相关的**，不是元素装饰——在战列舰截图上有，在底对齐那张上没有——因此不能用作底边缘。

得出的数字如下，两者都在**两种**对齐下对照装备架核验过，而非推导：

| | 旧值 | 2026-07-30 测得 |
|---|---|---|
| `SHIP_TOP_MARGIN` | 28 | **12** |
| `SHIP_BOTTOM_MARGIN` | 12 | 12（不变） |
| `HUD_NOMINAL.shipui.h` | 160 | **176** |

- 顶对齐：元素 12..188，装备架第 1 行在 `12 + 20 = 32`。**测得 32。**
- 底对齐：元素 `1440 − 12 − 176 = 1252`..1428，装备架第 1 行在 1272。**测得 1272。**

两者都精确命中，而这三个数字的其他任何组合都做不到。

**所以边距是相等的，上面声称相反的笔记是错的。** 那条笔记的推理是：下边距测得 12，上边距 28，因此元素在垂直方向不对称。12 是对的，28 不对——它从未被测量过，只是通过假定一个 160px 高、装备架位于其内 4px 的元素推出来的。测量钉住的只有装备架的位置，而仅有装备架位置无法确定元素自己的边缘：28/160 和 12/176 都能复现它。打破平局的是电容器。

一般性的教训，也是本节存在的原因：**一个能复现你所有测量的数字仍然可能是错的**，如果那些测量从未触及它所描述的东西。

### 舰船 HUD 效果行

**2026-07-31** 为画布细节层测量，取自五张截图：两张原生 2560×1440 顶对齐的（`effect.png`，一个效果；`effects.jpg`，两个）以及同一天提供的三张底对齐裁剪。偏移从元素自己的左上角起算，即 `HUD_NOMINAL.shipui` 描述的方框。

施加在你舰船上的 buff/debuff 图标画成一行，而**这一行不属于元素**。它完全位于方框之外，`HUD_NOMINAL.shipui.h` 保持 176。

| 部件 | 几何 |
|---|---|
| 效果图标 | ⌀36 圆形，列间距 **48** |
| 行放置 | **以电容器为中心**——方框 x 148，元素自己的锚点 |
| 间隙，顶对齐 | 行的首个发光行在方框 y **192**，即元素下方 **16** |
| 间隙，底对齐 | 行**翻转到元素上方**，在其上边缘之上 **16**（客户端代码；裁剪说 10） |

**该行以锚点为中心，不是以方框中心。** 两张原生截图把 HUD 放在相同位置，因此可以交叉核对：方框 x 在两张中都是 943，双图标截图的图标在屏幕 1049/1097（相对方框 106/154），而 `148 − (48 + 36)/2 = 106` 精确复现了它。单图标截图读为 131，预测为 130——那是图标的*美术*，一个 ⌀34 的青色 buff 对照另一张截图的 ⌀36 红色 debuff，不是布局差异。

#### 底对齐裁剪确定了什么，以及没确定什么

它们是**原生抓取的 2 倍放大**，不是原生截图。三把独立的尺子在该倍数上一致——图标直径（73/36）、UI 字体大写字母高度（29/14）、以及拟合到电容器量表带的圆（r 146 对原生 74）——这才允许除以它。

它们确定了两件事：

- **HUD 底对齐时该行翻转到元素上方。** 必须如此：底对齐的元素位于距屏幕底部 12px 处，因此悬在其下方的行会出屏。三张裁剪都把该行的底部放在电容器首个发光行之上 53 个放大像素，而那个发光行在元素上边缘之下 16 个原生像素，得出 `53/2 − 16 = 10`。**该间隙与下方的 16 并不对称**——那个不对称是测得的，不是假定的。
- **居中在高数量下成立。** 固定电容器轴，三行各自解出*整数*个槽位——11、10 和 11。为了让结果为整数，该行的其他任何东西都不必假定，而每张裁剪左侧被重叠窗口遮住的那两个图标正是让算式闭合的原因。没有那个核验，最左边*可见*图标看起来像该行的终点，该行看起来偏离中心约 50 个原生像素。

**2026-10-11 被客户端代码取代**——读本节的裁剪算术时记住这一点。该栏是一个 44 高的条带，放置在距 HUD 所对齐的任一屏幕边缘 `SHIP_UI_HEIGHT` = 200 px 处（`shipUI`：`buffBarContainer.top = SHIP_UI_HEIGHT`，像 HUD 容器一样对齐 CENTERTOP 或 CENTERBOTTOM），因此间隙**两个方向都是 16**。每个槽位都是 `SLOT_WIDTH` = 48 宽，带一个 40px 的图标框（`shipHud/buffButtons`），栏填充时没有任何东西使它们变窄：**间距永远是 48**。“上方 10”和“43 间距”都来自假定裁剪是精确的 2 倍放大。

有一件事它们**没有**确定：**间距随行增长而收紧。** 2 个图标时是 48；那些裁剪给出 86 放大 = 43。它们的其他一切都落在干净的 2.0 上，因此这是真实行为而非缩放错误——EVE 把繁忙的行排得更紧。`detail.ts` 对 48 建模但没有实现收紧，因此繁忙的行会画得宽百分之几，这对一个职责是显示窗口会与什么碰撞的画布来说是安全方向。一张已知数量的原生分辨率截图可以确定该规则。

### 目标列表效果行

**2026-07-31** 从 `target_effects.jpg`（原生 2560×1440）测得。偏移从一个槽位的左上角起算，与下文“目标列表锚点”同一坐标系。

| 部件 | 几何 |
|---|---|
| 效果图标 | ⌀25 圆形，列间距 **32** |
| 行放置 | 顶部在槽位 y **142**，以环的轴为中心（槽位 x 58.5） |

依据**标签行**而非环登记：环的明亮范围包含锁定括号，而标签测得的 13 间距与 `TARGET.labelPitch` 精确吻合——两件独立的东西在槽位起点上一致。标签文本自己的中心（2029.5）与环的（2030）也一致，这确定了水平轴。

**该行结束于 167，在 181 高的槽位之内**，因此 `HUD_NOMINAL.target` 无需调整，目标列表的占地不变。与舰船的行不同，这一行以固定数量 2 绘制：它是列表上每个槽位的装饰，而列表长度本身已是一个偏好。

### 战斗机 UI 内部结构

**2026-07-30** 从 `fighter.png`（原生 2560×1440，锚点 `(329, 289)`，4 个中队其中 3 个已发射）测得，同样的剖面方法。偏移从锚点起算——锚点即面板的左边缘与能力网格的顶部。

| 部件 | 几何 |
|---|---|
| 能力网格 | ⌀44 圆形按钮，从 x 70 起列间距 86，从 y 2 起行间距 50，3 行 |

与舰船 HUD 相同的两条教训：**一切都是圆的**，而且**左侧有一列从未绘制的控制按钮**。

**面板方框是客户端的容器，464 x 266**（2026-10-11 从 `squadronsUI` 读出）：一个自动定尺寸的方框，覆盖从中队 80 宽、从 x 40 起 86 间距排布，因此宽 `34 + 86n`、高 266。下面的数字是它的美术尺寸，且与代码一致：每个表盘是 x 40 + 86i 处 86 宽 `SquadronCont` 的美术（所以 ⌀81 居中于 42.5），能力图标位于 x 20 处 64 宽的 `AbilitiesCont` 中（居中于 92，即测得的 70..114）。最后一个表盘的容器比面板突出 3px，这就是美术测得 467 宽的原因。客户端还把存储的点钳制到 `x ≤ W − 32`、`y ≤ H − 266`。

**决定面板宽度的是中队行，不是能力网格。** 在 5 中队航母的最大值处 `42 + 86 × 4 + 81 = 467`，恰好是 `HUD_NOMINAL.fighter.w`；能力网格止步于 `70 + 86 × 4 + 44 = 458`。更早一轮曾通过假定网格延伸到边缘而*推导出* 53 的能力单元宽度——提醒：一个落在正确总数上的推导，仍可能在它所测量的东西上出错。

**控制列是面板最低的元素**，结束于 y 264——因此 `HUD_NOMINAL.fighter.h` 是 **264**，不是 2026-07-28 记录的 253。没有东西注意到，因为没有东西绘制控制列：旧数字止步于中队标签，那是编辑器已知的最低部件。

与舰船 HUD 高度相同的错误形状，相同的原因——方框按我们恰好在绘制的部件定尺寸，而不是按元素。

2026-07-30 对照完整的 `testdata/corpus` 树（184 个不同的 `core_user_*.dat` 文件）经语料验证。两个键都在账号文件的**根 `ui` 段**下——不是 `windows`（`neocomWidth` 所在处）——作为普通的 `(timestamp, value)` 叶子节点。本笔记的早期草稿类比 `neocomWidth` 假定了 `windows`；语料守护（`chat_panels_corpus.rs`）在发布前抓住了这个错误，方式与 `tests/hud_corpus.rs` 抓住 `badge_*` 假定 `ui` 而非 `notifications` 一样。

|---|---|---|---|
| 成员列表宽度 | `chatchannel_<ch>_userlistwidth` | Int — 50, 59, 72, 85, 102, 104, 107, 109, 119, 126, 127, 128, 135 | 86/184 |
| 输入框高度 | `chatinputsize_chatchannel_<ch>` | Int — 62, 63, 64, 70, 76 | 121/184 |

该截图还把两个键放在正确的单位上：分隔条在 190 处留下 104px 的成员列表，1376 下方的带高 62px，两者都是上面语料表为这些键给出的值。这是一致性，不是证明——这张截图背后的角色文件没有被取出，因此这里没有任何东西把存储数字与测量值钉在一起。

在写入任何东西之前，id 会先对照 `chatchannel_` 前缀校验。键名由窗口 id 拼接而成，因此未经校验的 id 会铸造出 `market_userlistwidth`——一个 EVE 从不读取、也从没有人清理的键。整批校验在第一个变异之前完成，因此被拒绝的写入会让文档保持逐字节相同。

2026-09-28 在游戏中于 Pilot Echo（`core_char_96000002`）、Alpha-Intel（`chatchannel_player_-70000002`，`ChatWindowStack` 的一个固定成员）上验证。

### 目标列表锚点

**2026-07-31 在游戏内抓取**（B1 Pilot Echo，2560×1440，UI 缩放 1.0）：三个位置、两种朝向、四张原生截图，按亮像素聚类测量。完整推导过程在 `docs/live-verification-target-origin.md`。

账号文件（`core_user_<id>.dat`），根 **`ui`** 段——*不是* `windows`：

- `targetOrigin`（`Tuple(Float, Float)`）——列表的锚点，约 13% 的账号文件。
- `targetOriginLocked`（`Int` 0/1）——位置锁定。与 `targetOrigin` 在同一事务中写入；为 1 时列表在游戏中无法拖动。
- `alignHorizontally`（`Bool`）——false 时列表纵向堆叠，true 时排成一行。

**段要从 `bmdump dump-inline` 读，绝不要从 `bmdump dump` 读。** 普通 dump 会把这些键一路回溯到 `windows`——`neocomWidth` 真正所在之处——在内联树定案之前，有两个账号文件正是这样被误读的。`tests/hud_corpus.rs::every_account_hud_field_reads_from_a_real_file` 是守护，它确实会在段错误时失败（已检查，不是假定）。

**这一对是一个分数，且两个轴不共享同一约定：**

```
anchor_y = f_y × screenH                    在全部四个已知值中精确
anchor_x = M + f_x × (screenW − M)          M = neocom 的绘制宽度
```

每个已知值都是精确的 `pixels / denominator` 有理数，机器级精确：2038/2512、1354/2488、531/2488、2053/2523。**M 是角色的 `neocomWidth`**——2026-10-11 从客户端代码定案。目标层被侧面板填充（`sidePanelsLayer.UpdateWindowPositions` 把 `uicore.layer.target` 上的 `padLeft`/`padRight` 设为 neocom 停靠那一侧的宽度），`targetMgr` 把原点的中心存为该层的分数：拖动时 `f = (x − N) / (W − N)`（`OnOriginMU`），加载时 `x = N + int(f × (W − N))`（`GetOriginPosition`），其中 N 是**读取时**的 neocom 宽度。因此调整 neocom 大小会移动列表。旧的谜题——“M 不是 `neocomWidth`，账号持有 37 而其写入值从 48 移到 72”——是账号文件的遗留键：角色的真实宽度从默认 48 变成 72。`layout.ts` 过去从值反推分母；现在它读取角色的宽度，与客户端一致。

**锚点是列表的外边缘；槽位从它朝屏幕中心延伸**，两个轴各自独立。同时解三个拍摄位置的缩放、原点与槽位偏移，得出锚点→第一个槽位中心的偏移为 55.5px，符号随侧翻转——恰好是测得的 110px 间距的一半，这是拟合中没有任何东西强迫的。

槽位间距为**横向 110、纵向 181**；目标环宽 79px 亮像素；锚点 → 第一个环中心沿生长轴 141px。朝向不移动锚点：一个存储值分别按纵向和横向拍摄，锚点槽位落在同一像素（标签中心 x 1369.0，环带 y 578..644）。

**在一个槽位内部**（偏移从槽位自己的左上角起算，供画布细节层使用）：锁定环是 x 19、y 0 处的 ⌀79——中心 (58, 40)。三行标签随后在 y 102、115 和 128，高 8px、13px 间距：两行名称，一行距离。它们测得的宽度（"Caldari Police / Commissioner / 29 km" 为 90 / 68 / 28）是名称的，不是元素的，每行左边缘距居中不到半像素——因此细节层把它们居中，不假装知道文本。更短的名称用更少的行；任何文件都没说用几行。

**写入方向已在游戏内确认**（2026-07-31）：通过编辑器设置的锚点画在画布所说的位置，两种朝向都是。只有一个铸造值仍未测试——那次会话编辑的是文件已携带的值，因此分母是反推的而非假定的。

**列表由分数而非像素决定转折**：当 `f > 0.5` 时槽位向左延伸，当 `fy > 0.5` 时向上延伸（`GetOriginPosition(getDirection=1)`），因此水平转折点在 `(W + N) / 2`，不是屏幕中点。

**EVE 自己的默认位置**——87% 的账号文件没有 `targetOrigin`，客户端从 Selected Item 窗口推导一个（`targetMgr.GetOriginPosition`，2026-10-11 读出）：它取该窗口的矩形（`selecteditemview`——或其默认值，宽 566、距右上 16、在高度 900+ 的屏幕上高 174、否则高 138，依据 `actionPanelDefaults`），从其左边减 15，并在窗口位于屏幕中点右侧时把锚点放在窗口左边缘、位于左侧时放在右边缘，两种情况都放在窗口顶部。横跨中点的窗口会把它送到 `(W − 300, 16)`。该矩形是窗口加上吸附在其上方的每个窗口的包围盒（`FindConnectingWindows('top')` + `GetGroupAbsolute`）：当一个窗口的左下角恰好落在某成员的左上角、或其右下角落在某成员的右上角时即加入，向上跟随，范围是在屏幕上且未堆叠进另一个窗口之内的窗口；最小化的 Selected Item 单独读取。编辑器对它计为重新打开的窗口做同样的事。在游戏中重置窗口设置会删除 `targetOrigin`，从而把列表放回这条规则上。画布在那里绘制列表，首次拖动会铸造两个轴。

### 总览标签页名称（客户端代码 + 游戏内核对，2026-10-09）

标签页名称由普通 `Label` 绘制，因此它接受标签的完整标记语言。`overviewWindow._ConstructTabs` 先做三件事：`name.strip()`（每个标签之外的空格永远到不了屏幕；标签之内的空格会到，pack 就是靠这个加宽标签页的），然后当标签页自己的 `color` 键被设置时，用 `Color.RGBtoHex(*color)` 把名称包成 `<color=%s>%s</color>`（所以名称内部的标记颜色胜出），然后 `tabGroup.AddTab`。该键由游戏内的标签页颜色选择器写为三个浮点的元组，例如 `(0.498, 1.0, 0.122)`；大多数标签页携带 `None`。

标记由原生分词（`trinity.ParseLabelText`，`_trinity_dx11.dll` 中的 `Tr2LabelTextParser.cpp`）并在 `carbonui/control/label.py`（`Parse*Open/Close`、`UpdateMeasurerProperties`）中应用：

| 标记 | 行为 | 游戏内（一个测试窗口，每个标签一种） |
|---|---|---|
| `<color=V>` | 堆叠；最内层胜出。`V` 是名称（`StringColorToHex`，在 Python `capitalize()` 之后匹配：Black, Green, Silver, Lime, Gray/Grey, Olive, White, Yellow, Maroon, Navy, Red, Blue, Purple, Teal, Fuchsia, Aqua, Orange, Transparent, Lightred, Lightblue, Lightgreen），否则 `#`→`0x` 并 `long(V, 0)` 作为 AARRGGBB；色盲模式可能重映射它 | 三种形式和半透明 alpha 都绘制；**`0xRRGGBB`（6 位）是 alpha 0，什么都不画** |
| `<b> <i> <u> <uppercase>` | 计数器 | 全部绘制 |
| `<fontsize=N>` | 堆叠；N 是像素，负 N 是字号预设（`check_convert_font_size`） | 8 和 16 都绘制；条带保持单行 |
| `<letterspace=N>` | 堆叠，每字母额外像素 | 绘制 |
| `<font color= size= file=>` | 颜色与大小的类 HTML 形式 | 绘制 |
| `<hint=…>` | tooltip | **文本从标签页上消失** |
| `<left> <right> <center>`、`<url>`/`<a href>`、`<localized>` | 对齐、链接、本地化 | 单行标签页上无可见效果 |
| `&lt; &gt; &amp; &nbsp;` | 实体 | `&lt;esc&amp;&gt;` 读作 `<esc&>` |

标签页标签的基础字号是 `EVE_MEDIUM_FONTSIZE`（Medium 客户端字体设置下为 14）。这台机器账号文件中所有标签页名称（48 个不同值）只使用 `<color>` 和 `<b>`，常常是名称一部分上色（`<color=…>*</color>  main`）。`crates/settings-model/src/tab_name.rs` 镜像这些规则；它是唯一的解析器与写入器，由应用和 MCP 共享。

### 总览列（实验 3a–3b：加一列，重排列）

列的可见性与顺序是**按总览标签页的**，存储在 `core_user_<id>.dat`（账号作用域），宽度按角色存在 `core_char_<id>.dat`：

- 可见集合 + 顺序：用户文件根 → `b"overview"` → `b"tabsettings_new"` → `(timestamp, dict)`，以标签页索引（Int）为键。每个标签页是一个字典：`"name"`（Str 标签）、`b"bracket"`（bracket 预设名）、`b"color"`（None 或 3 浮点 RGB 元组）、`b"overview"`（总览预设名）、`b"showAll"`/`b"showNone"`/`b"showSpecials"`（布尔）、`b"tabColumnOrder"`（列名 Bytes 列表，完整顺序）和 `b"tabColumns"`（列名 Bytes 列表，**可见**集合——给一个标签页添加 Transversal Velocity 会在此追加 `b"TRANSVERSALVELOCITY"`）。还有一个遗留的兄弟 `b"tabsettings"`（更旧的形状，客户端仍在重写）。
- 按标签页的键是带继承的稀疏键（实验 3b）：没有自己 `b"tabColumnOrder"`/`b"tabColumns"` 的标签页继承下面的账号默认值；在这样的标签页上首次拖动重排会**创建**该标签页自己的 `b"tabColumnOrder`（在标签页 0 上观察到：写入完整的 14 列列表，被拖动的列在其新槽位）。重排**只**触及用户文件——角色文件除时间戳外无变化。
- 账号级默认值：用户文件根 → `b"overview"` → `b"overviewColumns"`（可见集合）和 `b"overviewColumnOrder"`（顺序）——当单个标签页的列被编辑时**没有**变化；它们似乎是应用于没有自己设置的标签页的默认值。
- 宽度：角色文件根 → `b"ui"` → `b"SortHeadersSizes"` → `(timestamp, dict)`，以元组 `(b"overviewScroll2", tabIndex)` 为键 → 列名 → 宽度 px 的字典（添加该列为被编辑的标签页创建了 `b"TRANSVERSALVELOCITY": 159`）。兄弟 `b"SortHeadersSettings2"` 有同样的键控，保存按标签页的排序状态。宽度条目在标签页渲染时惰性出现。
### 总览状态、颜色与标签（切片 3；id 36/37 实验 2026-07-22）

哪些飞行员状态给总览行着色或携带 colortag 是**账号作用域的**，在 `core_user_<id>.dat` 根 → `b"overview"` 下，作为四个 `(timestamp, [int])` 键：

| 键 | 保存 |
|---|---|
| `backgroundStates2` | 给行着色的状态——**已启用子集** |
| `backgroundOrder2` | 按优先级排列的**每个**已知状态（首个匹配胜出） |
| `flagStates2` | 显示 colortag 的状态——已启用子集 |
| `flagOrder2` | 按 colortag 优先级排列的每个已知状态 |

- **启用与顺序相互独立。** 顺序列表枚举完整的状态全集，无论勾选了什么；`*States2` 列表是勾选的子集。因此切换一个状态只写 `*States2`，重排只写 `*Order2`——绝不会耦合写入。
- 一个干净的账号**四个键都没有**；客户端回退到其内建默认值。首次编辑只实体化被编辑的那个键。
- 无后缀的 `backgroundOrder` / `backgroundStates` **只**出现在 `overview → restoreData`（会话状态，仅原始树），因此与 `tabsettings` → `tabsettings_new` 不同，这里**没有遗留迁移**。

**三套词汇，不是一套。** 它们不同，混为一谈是错的：

| 界面 | 数量 | 内容 |
|---|---|---|
| 外观列表，按渲染 | 22 | 飞行员状态 |
| `backgroundOrder2` / `flagOrder2`，按存储 | 23 | 那 22 个加 `68` |
| 筛选 → Exceptions | 24 | 那 22 个加 id `36` 和 `37` |

id `68` **被存储但从不渲染**——对照一张完整窗口截图验证，它结束于第 22 位、下方留白，不是滚动折叠。它是一个保持用例，不是发现缺口：它必须在读/写往返中存活，且绝不能从顺序列表中被静默丢弃。id `36`/`37` 是两个非飞行员（残骸）状态，这就是它们只出现在 Exceptions 下的原因；2026-07-22 的一次真实实验确定了哪个是哪个——把“Wreck is empty”在游戏内设为 Hide 把 **37** 移进某个预设的 `filteredStates`，而 **36** 留在原处，得出 **36 = "Wreck is already viewed"，37 = "Wreck is empty"**。状态 id 在文件中不带标签，也没有 ESI 或 fsdbinary 来源；id→标签映射存在于客户端脚本中，因此编辑器捆绑一份手工编写的词汇表。

**`stateColors` 是稀疏的。** 同一容器，`(timestamp, dict)`，以**元组** `(surface_bytes, state_id)` 为键 → 0..1 浮点的 RGBA 4 元组。在一个启用了 20 个背景状态的语料账号中，只有 13 个带有条目：**缺失表示 EVE 对该状态的内建默认颜色，不是黑色。** 删除该键就是“重置为默认”的工作方式，绝不能与写入显式颜色混淆。`b"background"` 是整个语料中观察到的唯一 surface；任何其他 surface 都被读过去并原样写回。

按预设的**例外**存在于预设 blob 上（见下文 `overviewProfilePresets`），作为 `filteredStates`（隐藏）和 `alwaysShownStates`（总是显示）。两者在真实文件上互斥，因此编辑器把它们建模为每个状态的三态。

一个 `filterOut` 键——总览容器中一个 `(timestamp, None)` 兄弟条目——在 36/37 实验期间被观察到出现。它不是状态键，本切片不触及它。

- 总览 **pack**（EVE 的 Overview Settings → Misc Import/Export 写出的 YAML）把字典编码为二元素 `[key, value]` 序列的序列，并使用自己的词汇：`backgroundStates`/`backgroundOrder`/`flagStates`/`flagOrder`（文件的 `…2` 键去掉后缀）、`columnOrder`（`overviewColumnOrder`）、`presets`（`overviewProfilePresets`——bracket 预设是普通预设，由标签页的 `bracket` 字段引用）、`tabSetup`（`tabsettings_new`）、`stateColorsNameList`（`stateColors`，按调色板 NAME 而非 RGBA）、`stateBlinks`、`shipLabels`/`shipLabelOrder` 和 `userSettings`。
- `overview` → `restoreData` → `data` 按该 pack 词汇原样保存**最后导入的 pack**，`presetHistoryKeys` 是已导入 pack 的 MRU（按内容哈希为键，`overviewName` = pack 的名称）。把 `restoreData` 的 `stateColorsNameList` 与真实 `stateColors` 连接起来，就是推导出调色板（`darkBlue` = `(0.0, 0.15, 0.6, 1.0)`，……）的方式——见 `overview_pack.rs` 的 `PALETTE`。两个键对我们保持只读。

### 自动填充 / 已记忆字符串列表（实验 4：做了一次 People & Places 搜索）

客户端中所有已记忆的文本输入历史是**一个结构**，只在 `core_user_<id>.dat` 中（角色文件中不存在 `editHistory` 键）：

- 路径：用户文件根 → `b"ui"` → `b"editHistory"` → `(timestamp, dict)`；内层字典以 UI 小部件路径（Bytes，例如 `b"/addressbook/content/main/SearchPanel/Container/SingleLineEditText"`）为键 → 已记忆字符串列表（Str；偶尔一个空 Bytes 条目）。新条目追加在该小部件列表的末尾（测试搜索出现在 People & Places 搜索列表的最后一个元素）。
- 一个真实文件中观察到约 40 个小部件路径列表：People & Places 搜索、库存快速筛选、建筑浏览器搜索、技能目录搜索、舰队/装配名称、钱包转账"reason"、总览导出文件名、聊天频道名、bug 报告标题等。整个这个字典就是规范的 `SuggestionLists` 类别：编辑器可以通用地枚举键并提供按列表的添加/删除/重排/清空，而不需要硬编码的小部件列表。

- 总览*筛选预设*（标签页内容）存在于用户文件根 → `b"overview"` → `b"overviewProfilePresets"`（以预设名 Str 为键的字典），兄弟有 `b"overviewProfilePresets_notSaved"`、`b"presetHistoryKeys"`、`b"restoreData"` 作为会话状态——按规范 §6 在 V1 中仅原始树。

### 真实账号上的 `tabsByWindowInstanceID` 形状（总览 pack 审查，2026-07-26）

**任何写入该键的东西都必须写完整的映射**——漏掉一个标签页会把该标签页在游戏中藏起来，漏掉所有标签页会把整个总览藏起来。这就是为什么 `create_window_mapping` 拒绝（而不是跳过）它读不出键的标签页，以及为什么没有其他路径可以创建该键：缺失的映射是正常状态，因此*部分*的映射严格比没有更糟。EVE 自己的总览导入器干脆删除该键——证据与抓取见上文“我们的 pack 导出 vs EVE 自己的”（2026-07-28 确认）。

在修复一个 pack 导入 bug 期间对完整 1925 账号语料做了测量（一次重新导入重新指向该映射，导致一个标签页索引跨两个窗口重复）：1925 个语料账号中，**825 个带有 `tabsByWindowInstanceID` 映射**；**其中 823 个恰好有三个窗口**；**其中 812 个按 6+1+1 分割**（一个“其他所有”窗口装六个标签页，两个单标签页窗口）。如此失衡的映射正是会让朴素的“给窗口 0 所有标签页，然后过滤其余”重新指向出错的形状：窗口 0 必须由*其他窗口不认领*的东西构建，而不是反过来。

### 快捷键（规范 `2026-07-26-keybindings-editor-design.md` §2.1–§2.2）

路径：`core_user_<id>.dat` 根 → `b"cmd"` → `b"customCmds"`。

```
root → cmd                      bare Dict, NOT timestamp-wrapped
     → customCmds               Tuple(FILETIME, Dict)   ← ONE stamp, whole table
          → { Bytes command : value }
                None            unbound
                Tuple(Int…)     [17?, 18?, 16?, key]
```

在 2026-07-22 语料快照上测量：**132 个账号文件中共 12,117 个绑定条目**（按路径，在那一个快照内——其中另外 43 个文件的 `customCmds` 为空；`keybinds_corpus.rs` 中的语料门禁测试在跨所有快照去重逐字节相同的文件后测得 97——两个计数都对，只是基数不同）。12,117 个条目中，4,765 个已绑定，7,352 个为 `None`。

**值包装约定的例外。** `customCmds` 把 `(FILETIME, value)` 包装器放在*容器*上；里面的叶子是裸的——与通常的放置相反（见上文“值包装约定”）。在一个真实 TQ 账号上验证：`Tuple[1]<Int(82)>`、`Tuple[2]<Int(16), Int(83)>`。该取样真实文件的 93 个叶子中 0 个被包装。包装其中一个会产生一个畸形值，客户端忽略它同时保留其过时的绑定。

在 4,765 个已绑定条目上，五条不变量**零例外**地成立：

| 不变量 | 证据 |
|---|---|
| 每个绑定恰好一个非修饰键码 | `{1: 4765}`——没有绑定有 0 个或 2+ 个 |
| 修饰键在键之前 | 4,765/4,765 |
| 修饰键顺序为 Ctrl(17) → Alt(18) → Shift(16) | `Alt+Shift` = `(18,16,…)`，`Ctrl+Alt+Shift` = `(17,18,16,…)` |
| 文件内无重复组合 | 132 个文件中 0 个含重复 |
| 字典键是 `Bytes` | 132/132 个文件 |

观察到的组合：无（1,575）、Alt（1,282）、Ctrl（1,004）、Shift（768）、Alt+Shift（131）、Ctrl+Alt+Shift（5）。元组长度 1–4。

无重复的结果意味着 **EVE 强制唯一性**：重新绑定一个已在使用的组合会从其原主人那里偷走它。

**客户端对该表做了什么**，2026-10-10 从其代码读出（carbonui/services/command.py、eve/client/script/ui/eveCommands.py）。工厂绑定存在于代码中（`SetDefaultShortcutMappingCORE` + `SetDefaultShortcutMappingGAME`；应用的副本由 `tools/gen-commands.py` 生成）。加载时，`CommandMap.AddCommand` 给每个命令其 `customCmds` 值（如果它有一行），否则给默认值——**除非任何存储值等于该默认值**，此时该命令起始为未绑定。重新绑定（`MapCmd`）用 `ClearMappedCmd` 清除该组合的当前持有者，它写入那个命令的 `None`（需要时添加其行），然后 `RemapCommand` 写入新主人的行。这就是为什么表中大多是 `None`：它们记录每一次偷取与解绑，不只是绑定。“重置为默认”写入 `customCmds: {}`。

取样文件的 `cmd` 根键是普通 `Bytes`，但兄弟根键可以是 `Ref`/`Shared`（与上面账号文件的 `ui` 键同样的陷阱），因此段查找仍必须经 `effective` 解析，而不是直接对段键匹配 `Value::Bytes`。

### 名称存在性（任务 11 决策：本地提取不可行）

在当前客户端的新鲜文件上调查，账号的真实角色名称通过带外已知（名称经交互式验证，从不记录在此）：

- 角色文件**不**结构化地存储其自己角色的名称。它甚至不包含自己的角色 ID——ID 只存在于文件名中。
- 用户文件**完全没有** characterID→name 结构；该账号三个角色 ID 没有一个出现在其解码树的任何地方。
- 找到的每个名称出现都是附带的 UI 状态：聊天频道标签（一个以角色命名的频道）、形如 `containerWnd_<CharacterName>'s Capsule` 的容器窗口 id（胶囊货舱窗口，在**用户**文件中）、嵌入飞行员名称的停靠容器键，以及 editHistory 搜索字符串（被搜索的*其他玩家*名称）。
- `core_public__.yaml`（机器音频/设备设置，YAML 中同样的 `(FILETIME, value)` 约定）和 `prefs.ini` 不含名称。

**规范 §6 的决策：** ESI `POST /universe/names` 是角色 ID 的主要解析来源（批量、缓存、离线安全、可禁用）；账号 ID 用用户别名。本地提取降级为*仅建议*的启发式。

**账号↔角色关联（可行）：** 登出时客户端在几秒内先后写入所玩角色的 `core_char` 与其账号的 `core_user`（观察到相隔 3 秒），因此 mtime 聚类是可靠的“角色 <id> 的账号”建议。较弱的文件内佐证提示：用户文件的胶囊容器窗口 id 嵌入账号自己角色的名称（不可靠——胶囊可以改名；仅建议，按规范 §6 的确认进别名流程）。

**引导抓取的账号写入触发器（M3b 真实冒烟，2026-07-15）：** 受控登出的抓取需要一个*账号级*改动使 `core_user` 前进（所玩角色的 `core_char` mtime 无论如何都会在登出时前进，由此识别角色）。已确认可靠的触发器：切换 **Camera Shake**（Settings → Display & Graphics），一个账号作用域的图形设置——这就是应用的抓取对话框所举的例子。按上面映射的其他账号级写入方：任何 Display/Graphics 或 Audio 设置；总览列的添加/删除/重排（`overview → tabsettings_new`；角色文件只更新时间戳）；总览筛选预设编辑（`overview → overviewProfilePresets`）；或在自动补全字段中输入以追加到 `ui → editHistory`。（M3b 放弃了被动名称匹配的建议层级——解析每个用户文件会冻结 UI——因此手动配对 + 这次抓取是实际发布的关联路径。）

### Neocom 按钮（语料调查，非游戏内抓取）

布局深度里程碑规范曾预期这个切片（neocom 按钮编辑器）需要自己的游戏内抓取实验，因为 `btnType` 和 `children` 语义尚未映射。结果不需要：对真实语料的调查（一个后来删除的 `crates/settings-model/src/bin` 探针）覆盖 **4,215 个角色文件——其中 4,061 个携带该键，共 43,430 个按钮**——解决了抓取会有的每个问题。

- **位置：** 角色文件，根 → `b"ui"` → `b"neocomButtonRawData"`，包装为 `(timestamp, List[Instance])`。注意与 `neocomWidth` 的不对称（账号侧——见上文“HUD 锚点”）：*栏*按角色，其*宽度*按账号。

#### Neocom 顶部磁贴

**两个磁贴位于按钮列上方，且都不在键里：** EVE 菜单（汉堡）和角色头像。2026-08-01 从 `neocom_docked.png`、`hud_battleship.png` 和 `hud_frigate.png`（原生 2560×1440，三张都带 48px 栏）测得：菜单磁贴是行 0–47，头像 48–95，第一个真实按钮从 96 开始。两者都是一个栏宽的正方形，与按钮遵循的同一规则，因此**预留是 2 × `neocomWidth` 并随栏缩放**——画布在此之前发明了一个固定 40。两个磁贴在 `neocom-buttons.json` 中都没有 id，这本身就是语料对它们是装饰而非条目的确认。

所有截图中只观察到一种栏宽，因此“2 × 宽度”是从磁贴为正方形读出的，而不是从两个宽度与常量不符读出的。一张不同 `neocomWidth` 的截图会直接定案。
- **类：** 总是 `utillib.KeyVal`——43,430/43,430，未观察到其他类。
- **键集：** 在*真实栏*上，每个实例恰好是 `btnType, children, iconPath, id`，43,430/43,430，毫无变化。编写一个是固定的四键字典。**这对 `Original` 不成立——见下文。**
- **`btnType`** 取四个值，每个都是*按钮是什么*的属性，不是用户设置：`10` 每个文件恰好出现一次且总是在 `chat` 上；`21` 只在 `airCareerProgram` 上；`4` 在库存家族（`inventory`、`InventoryStation`、`InventoryStructure`）上；`1` 在其他所有上（34,593 个）。
- **`children`** 是 `None`（40,339）、空 `List`（2,585）或单元素 `List`（506）——绝不超过一个子节点，且作为子节点见过的唯一 id 是 `InventoryStation` 和 `InventoryStructure`。这些就是里程碑规范担心是用户自建文件夹的 Inventory 停靠上下文变体；它们不是。
- 整个语料中 **24 个不同 id**。更早一个探针报告 25：它把未解析的 `Tuple(bytes, None)` id（下面的异常）渲染成自己的占位字符串而不是解析为它包装的 id，并把该占位符计为第 25 个不同 id。24 是正确计数。
- **一个畸形形状：** 11 个按钮的 `id` 是 `Tuple(bytes, None)` 而非普通 `Bytes`。罕见、真实，读取时必须容忍、写入时必须保留——重写它就是对客户端本意的猜测。
- **`neocomButtonRawDataOriginal`** 包装在 8–14 个条目的 `Tuple` 中而非 `List`，而且——与本笔记过去所说相反——*不是*相同的实例形状。**它的按钮根本不带 `iconPath` 键：** 在拥有它的 102 个文件中，1226 个 `Original` 按钮全部 1226 个如此，对照同文件中 1126 个真实栏按钮的 0 个。`Original` 是三键字典，真实栏是四键。上面的 43,430/43,430 键集数字是在真实栏上测得的，对 `Original` 从不成立。

  这很重要，因为两种形状在编辑器中相遇。`read_button` 把缺失的 `iconPath` 映射为 `""`（`neocom.rs:102`），`addableButtons` 让一个 `Original` 条目覆盖目录中的（`neocom.ts:39`，刻意如此——它来自角色自己的客户端），因此从 `Original` 添加一个按钮会写出一个 `iconPath` 为空字符串的四键实例。**缺失键与空字符串不是一回事**，而空字符串是没有观察到任何客户端写过的形状。EVE 把它当作字面路径（空白图标）还是当作 falsy（按 id 回退）是一个待验证问题——见真实验证计划 §4，Phase 2，step 2。`reset()` 不受影响：它逐字复制 `Original` 的原始值（`neocom.rs:260`），写出真正的三键按钮。

**`Original` 是过时快照，不是目录。** 携带该键的约 4,061 个文件中只有 **495** 个其真实栏是自己 `Original` 的子集。九个 id 经常出现在真实栏上而*不在* `Original` 中——`fleet`（3,509 个文件）、`accessgroups`（3,465）、`corporation` 和 `structurebrowser`（各 3,454）、`log` 和 `notepad`（各 3,443），加上 `contracts`、`job_board` 和 `shipTree`——而且 `Original` 的时间戳比真实栏的更旧：客户端写过它一次，后来的补丁添加按钮时没有回头改它。与此同时 **3,454 个文件相对 `Original` 有按钮被移除**（最多 9 个），所以移除是玩家真的会做的事。因此 `Original` 可用作*一个*可添加按钮的来源以及重置基线，但它不是“存在哪些按钮”的答案——编辑器捆绑的目录提供其余部分，在前端与 `Original` 取并集。

### EVE 启动器记录角色↔账号归属（2026-08-13）

两个设置文件都没有说明角色属于哪个账号。在 `2026-07-27T131810Z_baseline` 语料、每个配置档文件夹上测量，检查每个文件是否以 LE32、LE64 和十进制 ASCII 双向含有对方种类的 id：**零命中**。这把 M0 的发现（角色文件不包含自己的角色 id）扩展到了交叉引用。

文件内名称启发式也死了，且现在是测得而非假定：对照真实 Tranquility 配置档上已知正确的映射，角色的 ESI 名称唯一识别其账号的比例是 27 个角色中 **4 个**。大多数名称出现在文件夹中*每个*账号文件里——聊天频道标签和联系人列表，不是归属。

**启动器确实说明了这一点**，在 `%APPDATA%\EVE Online\logs\eve-online-launcher-*.log`。在 Linux 上启动器运行于 Proton 之下，因此同一路径位于 prefix 内：`<steam library>/steamapps/compatdata/8500/pfx/drive_c/users/steamuser/AppData/Roaming/EVE Online/logs`（2026-09-11，一份库位于 `~/.local/share/Steam` 的报告）。它旁边的 `Documents/EVE/logs` 文件夹是游戏客户端的——Chatlogs、Gamelogs、Marketlogs——无论在 Windows 还是 prefix 中都从不存放启动器日志。

```
[esi] Fetching character details for <char_id>, <char_id>, <char_id>
[esi] Fetched 3 character details for <user_id>
```

这两行相隔几行，中间夹着无关输出。在一个真实安装上：**186 组配对观察 → 10 个账号，每个恰好 3 个角色，完全不相交**，每个 `user_id` 都匹配一个发现的 `core_user_<id>.dat`。日志保留回溯到 2023-11（98 个文件，8.1 MB），因此覆盖不限于近期会话。

两个风险，都在 `launcher.rs` 中处理：并发启动会交错这对行（189 行 `Fetching` 中有 3 行没有匹配的 `Fetched`），以及一个账号的角色集合在多年日志中会合法变化。解析投票，偏好每个账号最近的幸存集合，并丢弃任何被两个账号认领的角色。

还存在但未使用：`[client-queue] Queued client startup { userId, characterId: <slot>, profile: '<name>' }`，它还指名配置档文件夹。那里的 `characterId` 是槽位索引，不是角色 id。

### 舰队广播设置、监视列表颜色与阵型（2026-09-18）

一切都位于根 `ui` 下，每个叶子都带 `(FILETIME, value)` 包装；Broadcast Settings 对话框在账号文件，监视列表与阵型面板在角色文件。在 513 个不同文件加 B1 上两次真实抓取上测量——表见 `docs/superpowers/specs/2026-09-18-fleet-editor-design.md` §2。下一位读者需要的四件事：

- **`listenBroadcast_<Type>` 键只在其复选框被切换时写入。** 十六种类型中有八种在任何文件中都没有键；第九种 `WarpTo` 只在 2026-09-18 的抓取中有一个。它们的默认值是勾选。每个账号都携带的七种默认为约 93% 账号所持有的值（五个关，两个开）。
- **顶部复选框写两个键**——`listenBroadcast_ShowOwnBroadcasts` 和一个裸的 `ShowOwnBroadcasts`——同一瞬间，同一值。两个都要写。
- **EVE 的 ✕（无颜色）写 `(ts, None)`**；该键不被删除。缺失表示该类型的默认值，对四种类型是一个颜色，其余是无。
- **打开对话框会用一个 FILETIME 重新盖章每个已有的广播键。** 显示 25 个时间戳变动的抓取 diff 是一次对话框打开，不是 25 次编辑。

选择器是九个色板：黄 `1.0,0.7,0.0`、橙 `1.0,0.35,0.0`、红 `0.75,0,0`、绿 `0.1,0.6,0.1`、青 `0.0,0.63,0.57`、蓝 `0.2,0.5,1.0`、darkBlue `0.0,0.15,0.6`、黑、白 `0.7,0.7,0.7`——监视列表成员上是同一个选择器。已保存的舰队配置（"Form fleet with setup"）不在文件中：机主的名称只出现在账号的 `editHistory` 中（"Store fleet setup" 对话框），八个中有两个在任何地方都找不到，而客户端仍然列出它们。

### 舰船槽位顺序（2026-10-02）

`ui -> slotOrder`，账号文件，`(FILETIME, {shipItemID: [24 Int]})`。从客户端代码读出（`eve/client/script/ui/inflight/shipHud/__init__.py`、`slotsContainer.py`，从 `code.ccp` 解码）并在 157 个账号文件上测量（21,720 个条目，每个都是 24 个来自 11–34 的标志）：

- 键是 `session.shipid`，舰船的 item id，因此一个布局属于一个船体，不是一种舰船类型。id 约 1e12，因此线上是 `Long` 键。
- 值是 24 个装备架标志的一个排列：低槽 11–18，中槽 19–26，高槽 27–34。`InitDrawSlots` 读取 `myOrder[r * 8 + i]`，因此位置 `p` 是行 `p // 8`（网格 `[[1.0, 0.0], [1.5, 1.0], [1.0, 2.0]]`：顶部、中间错开半个按钮、底部）和列 `p % 8`。
- 当舰船没有条目时 `GetSlotOrder` 回退到 `[Hi0..7, Med0..7, Lo0..7]`。`SwapSlots(flag1, flag2)` 是唯一的写入方，且从没有东西删除条目，因此该映射随每一艘被重排的舰船增长。
- 过短的列表在 `InitDrawSlots` 中抛出，缺失的标志在 `SwapSlots` 中抛出。编辑器只写完整排列。

由 `crates/settings-model/src/slot_order.rs` 编辑；规范 `docs/superpowers/specs/2026-10-02-slot-order-design.md`。
