# 抓取：`targetOrigin` —— 它以什么为锚点，单位是什么

一次游戏内抓取，一个角色，一次登出。它敲定最后一个未建模的
屏幕部件键：`targetOrigin` / `targetOriginLocked`，据信是
锁定目标显示的锚点。方法见实机验证计划的 §4 —— 两个
点，因为单次读取无法把原点与缩放分开。

## 要敲定的是什么

`core_user_<id>.dat` → 根 **`ui`** 节：

```
b"targetOrigin":       (ts, (Float, Float))   # 0..1, normalised against something
b"targetOriginLocked": (ts, Int 0/1)
```

**从*内联*转储中读取该节。** 普通的 `bmdump dump` 会把这些键
放在一个能回溯到 `windows` 的位置 —— `neocomWidth` 实际就在那里。
只有 `dump-inline` 才能把共享解析成真正的树，而它们在树中位于
`ui` 之下，与 `neocomWidth` 相隔两节。这就是 `badge_x` 陷阱
（v0.15.0 声明 `ui`，该键却在 `notifications` 之下）把两个节对调的
版本，而且任何手工构造的测试夹具都抓不到它。

角色文件中没有任何与目标相关的内容 —— 对语料中每个
`core_char_*.dat` 做字节扫描，只在总览分组名内找到 `target`，
而整个快照角色文件中 243 个键的深度-2 全域里没有任何候选 ——
所以如果目标列表有存储位置，这对键就是它。它出现在语料中约 13 % 的
账号文件里，且在每个快照中恰好只有两个不同的值，这就是“拖动时写入”
的特征，与另外三个锚点相同。

三个问题，按回答成本排序：

1. **这对键究竟属于目标显示吗？** 目前还没有证据 ——
   名字是唯一的线索。切换锁定就能顺带回答它。
2. **x 是相对什么归一化的？** `y` 在两个已知语料值中都是屏幕
   高度上的精确像素（`7/72` = 140/1440，`67/96` = 1005/1440）。
   `x` 在 2560 上*不是*精确像素：`0.8113057…×2560 = 2076.94`。候选
   分母：2560、2523（= 2560 − `neocomWidth` 37）、2512。
3. **它指定的是元素的哪个点** —— 角，还是中心？战斗机面板
   用惨痛的方式教会了这一点：元素的可见范围随内容变化，
   锚点并不总在可见部分之内。

## 之前 —— 记录于 2026-07-31，客户端关闭

快照 `testdata/corpus/2026-07-31T000558Z_target-origin-before`（175 个文件，
仅 `settings_Default`），用 `tools\sync-corpus.ps1` 抓取。

```
targetOrigin       = (0.8113057324840764, 0.6979166666666666)
targetOriginLocked = 1
neocomWidth        = 37
shipuialigntop     = True
```

在 2560×1440 下，这读作右侧、大约三分之二高度处。（朴素的
“两轴都是整个屏幕的分数”给出 (2076.9, 1005.0)；y 是对的，
x 不对 —— 见下面已解出的约定。）这就是第 1 点：“之前”的
截图就是把画面与这些数字配对的东西。

## 游戏内步骤

- [ ] **1.** 只登入 Pilot Echo。离港并锁定**一个**目标（带里的一颗
      小行星就够 —— 什么都没锁定时目标列表不会绘制）。
- [ ] **2.** 截图，原始分辨率，不缩放。这就是第 1 点的那张图，
      必须与上面的数字吻合。
- [ ] **3.** 再锁定**两个**。*不移动任何东西*再截一张。同一个存储值下的
      两张截图才能说明列表从锚点向哪个方向生长 —— 与当初把舰船 HUD 的
      电容轮锚点同元素自身中心分开所用的手法相同
      （战列舰与护卫舰挂架的对比）。
- [ ] **4.** 如果拖不动，就解锁位置。无论用什么控件 ——
      在列表上右键，还是 UI 锁定开关 —— **diff 中 `targetOriginLocked`
      由 1 翻成 0，就是这对键属于目标显示的证明。** 如果没有任何东西
      能翻转它，这对键就是别的东西，本次抓取剩下的部分就是在测错对象。
- [ ] **5.** 把列表**横向拖远** —— 拖进屏幕左侧三分之一，
      与每条边都拉开距离。水平距离才能区分三个候选分母
      （在当前 x 下它们只相差约 8 px，在肉眼误差之内）。
      **绝不要拖到角落：角落会钳制，**
      钳制后的值不是你拖到的值。
- [ ] **6.** 在新位置截图，仍然锁定三个目标。
- [ ] **7.** 退出客户端。EVE 在登出时写入设置，而不是在更改时。

快照 `2026-07-31T010914Z_target-origin-after`，diff 在
`testdata/dumps/2026-07-31T010914Z_target-origin-after__vs__2026-07-31T000558Z_target-origin-before`。

```

```

**Q1 已回答 —— 这对键属于目标显示。** 解锁列表翻转了
`targetOriginLocked`，把仅时间戳的扰动从账号文件 diff 中剥离后，
除了这两个键和一处无关的聊天标签页变更，*什么也不剩*。
Pilot Echo 的角色文件只变动了聊天/窗口状态 —— 没有目标键，这
就终结了这些是否按角色而异的问题。并非按角色。

**Q2 半回答 —— y 是纯粹的屏幕分数。** 三个已知值都是
整个屏幕高度上的精确整数：`7/72` = 140/1440，`67/96` =
1005/1440，`47/90` = 752/1440。原点在顶部。

**Q3 由第二次会话回答**（快照 `2026-07-31T012708Z_target-origin-after2`）：
第三个位置加一次方向切换。

```
targetOrigin        (0.5442122186495176, 0.5222222222222223) → (0.21342443729903537, 0.5333333333333333)
alignHorizontally   False → True      ← the vertical/horizontal target layout toggle, root `ui`
```

**`alignHorizontally` 是方向标志** —— `False` 把列表纵向堆叠，
`True` 把它排成一行。它位于账号文件的根 `ui` 节中，紧挨
`targetOrigin`，在这次抓取之前一直没有被识别出来；
`docs/settings-field-reference.md` 把它归入 "Misc UI"，与地图键放在一起。

## 约定 —— 于 2026-07-31 解出

四张截图，原始 2560×1440，两次会话 UI 缩放均为 1.0
（`core_public__.yaml` 只显示时间戳在移动）。位置用亮像素聚类测量，
并以 `NN km` 标签行为锚点，该行在每张截图中都是 28 px 宽，
因此可重复到远小于 1 像素。

| 截图 | 存储值 | 方向 | 锚点槽 `km` 标签中心 |
|---|---|---|---|
| `target.png` | (0.8113057…, 0.6979167…) | 纵向，2 个目标 | (2034.0, 955.5) |
| `vertical.png` | (0.5442122…, 0.5222222…) | 纵向，3 个目标 | (1369.0, 702.5) |
| `horizontal.png` | 同一值 | 横向，3 个目标 | (1369.0, 702.5) |
| `horizontal2.png` | (0.2134244…, 0.5333333…) | 横向，3 个目标 | (657.0, 718.5) |

**y** 是纯粹的屏幕分数：`A_y = f_y × 1440`，在四个值中全部精确
（140、1005、752、768）。

**x 是相对 neocom 右侧的屏幕宽度归一化的**：

```
A_x = M + f_x × (screenW − M)          M = the neocom's drawn width
```

而存储的浮点数是一个*精确*有理数 `p / (screenW − M)` —— 机器级精确，
不只是接近：

| 值 | 精确形式 | 隐含的 M |
|---|---|---|
| 0.8113057324840764 | 2038/2512 | 48 |
| 0.5442122186495176 | 1354/2488 | **72** |
| 0.21342443729903537 | 531/2488 | **72** |
| 0.813713832738803（其他配置档） | 2053/2523 | 37 |

72 是实测的，不是拟合出来的：在 `target.png` 中，neocom 遮住了星云直到
x = 71，背景在 x = 72 处恢复。**这意味着 M 可以从存储值本身恢复**
—— 取精确有理数，`M = screenW − 分母`。这一点很重要，因为 M *不是*
`neocomWidth`：这个账号自 2022 年起 `neocomWidth = 37` 一直未变，
而它的写入却从 48 移到了 72。（72 究竟是玩家调整过大小的 neocom，
还是该设置的某个其他函数所决定的绘制宽度，
尚未确定，且不阻碍这套算术。）

**锚点在列表的外缘，列表向屏幕中心生长。** 一次解出三个位置的缩放、
原点和槽偏移（两个右锚定，一个左锚定），得到从锚点到第一个槽中心的
偏移为 **55.5 px**，符号随所在侧翻转 —— 恰好是 110 px 水平间距的
一半，而拟合中没有任何东西强制这一点。原点解出为
70.5，与从 neocom 实测的 72 相对。

**方向不移动锚点。** `vertical.png` 和 `horizontal.png` 拍摄于同一个
存储值，锚点槽在两张图中落在*同一像素*（标签中心 x 1369.0，
环带 y 578..644）。列表以锚点槽为轴旋转；其余的从它扇出。

### 元素几何，UI 缩放 1.0

| | |
|---|---|
| 槽间距，纵向 | **181 px** |
| 槽间距，横向 | **110 px** |
| 环的亮区范围 | 宽 79 px |
| 锚点 → 第一个环中心 | 沿生长轴 141 px，横跨向内 55.5 px |
| 锚点 → 第一个 `km` 标签中心 | 向上 49.5 px，向内 55.5 px |

因此一个 N 目标列表占据，右锚定时：x `[A_x − 111, A_x]`，y
`[A_y − 181N, A_y]` 纵向；x `[A_x − 110N, A_x]`，y `[A_y − 181, A_y]`
横向。左锚定时在 x 上镜像。

## 之后

`crates/settings-model/src/hud.rs` 中的四个 `Field` 条目，全部是
`HudScope::Account` 且全部 `section: b"ui"` —— **不是** `b"windows"`：
`targetOrigin` `elem: Some(0)`/`Some(1)`（`HudKind::Float`），`targetOriginLocked`
以及 `alignHorizontally`。然后 `HUD_NOMINAL` 加入 110×181 的槽，
`layout.ts` 加入与之匹配的放置/逆变换对，由 `layout.test.ts` 做往返验证。

**x 这一对不是通常的 `px ↔ 分数` 换算，绝不能按那种方式写入。**
分母是 `screenW − M`，而 M 只能从被编辑的值本身得知
（恢复精确有理数，`M = screenW − 分母`）。
两个后果：

- 优先以**增量**方式编辑：`f_new = f_old + Δpx / denominator(f_old)`。这
  永远不需要 M，而且精确。
- 一个**铸造**出来的值 —— 键缺失，或某个 Layout 预设把一个账号的值
  带到另一个账号 —— 没有可恢复的分母，也无从得知目标账号的 M。写入一个
  值就是猜测；诚实的选项是兜底到语料典型的 M = 72 并在 UI 中说明，
  或者拒绝铸造。在本功能发布前决定，因为 `batch.rs` 会很乐意携带这个字段。

`targetOriginLocked` 比看上去更重要：为 `1` 时列表在游戏中无法拖动，
所以编辑器写入的值就是玩家无法手工纠正的值。

账号范围意味着一次拖动会为**该账号上的每个角色**移动它，
与 `neocomWidth` 相同。UI 必须说明这一点。
