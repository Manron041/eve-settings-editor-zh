# 实机验证计划

编辑器已发布或即将发布的、所有**从未在运行中的 EVE 客户端上验证过**的内容，按启动客户端次数和手动步骤最少的方式编排。

九个切片在合并时没有附带实机冒烟测试，横跨 0.13.0 到 0.21.0。本计划一次性清空全部，而不是一次重新登录地逐个推进。

---

## 1. 成本模型

只有两样东西是昂贵的，而检查本身不在其列：

| 步骤 | 成本 | 备注 |
|---|---|---|
| 启动客户端并登录 | 分钟 | 需要最小化的单位 |
| 在角色选择界面切换到另一角色 | 秒 | **会重新读取该角色的文件** |
| 编辑器编辑并保存 | 秒、离线、不限次数 | |
| 回读文件 | 秒、可脚本化 | 见 §3 |

三条推论贯穿整个计划：

1. **EVE 在登出时写入设置，在登录时读取。** 每次抓取都是*操作 → 登出 → 读取*。编辑器写入的任何更改都必须在该角色**已登出**时保存，否则客户端会在退出途中将其覆盖。
2. **角色级状态免费成倍增加。** 登出到角色选择会写入离开的那个角色并读取进入的那个角色。因此在 *N* 个角色上预置的 *N* 个变体只花**一次启动**，而不是 *N* 次。账号级状态（`core_user_*`）则不然：它需要第二个账号，也就是第二个客户端——把它们并排运行，那仍然算一次启动事件。
3. **每次登录都身兼两职。** 先观察所有离线预置的内容，*然后*执行下一次抓取所需的游戏内操作，然后退出。绝不要把一次登录只花在一个方向上。

目标：**两次客户端会话**，第三次仅用于确认修复。

### *不*需要客户端的部分

用原始 Tree 视图离线制造边界情况的起始状态，而不是在游戏中寻找或创造它们——删除 `customCmds` 就得到一个从未打开过快捷键界面的账号；删除 `tabsettings_new` 就得到那 385/1925 个没有标签页设置的账号之一。两者在树中都是一键操作，否则两者都是一场试用账号搜猎。

**在一个同时带有旧版 `tabsettings` 的账号上，仅删除 `tabsettings_new` 是不够的。** `overview.rs::migrate_legacy_overview` 会在下一次总览编辑时把旧版重命名为现代版，但*仅当 `tabsettings_new` 缺失时*——而这正是删除所制造出的状态。于是下一次编辑会悄悄地以现代版的名称复活旧版表，零标签页路径永远不会运行。账号 B 同时拥有这两个键，第一次尝试时发生的正是这种情况。**删除两个键**，并在导入前确认该账号两者皆无。

## 3. `tools/capture-diff.ps1`

每次抓取都是"哪些字节动了"。在 Tree 视图里用肉眼做这件事是本计划手动步骤的最大单一来源，因此将其脚本化：`capture-diff.ps1` 以标签对实时目录做快照、解码它，并与之前的标签做 diff。

```
tools\capture-diff.ps1 -Label baseline                        # prep, snapshot only
tools\capture-diff.ps1 -Label after-session-a -Against staged-1
tools\capture-diff.ps1 -Label X -Against Y -NoSnapshot        # re-read two old labels
```

在**每个**阶段边界都运行它——每次离线预置之后、每次客户端退出之后——这样每个 diff 都恰好隔离出一个操作者，编辑器或客户端。快照落在 `testdata/corpus/`，解码文本落在 `testdata/dumps/`，两者都被 gitignore：它们是真实的个人数据，绝不能提交。它只通过 `sync-corpus.ps1` 读取实时目录。

它做的两件对读出体验有影响的事，都在历史 `exp1` 抓取上测量过：

- **只解码字节发生变化的文件。** 这里的实时设置目录有 586 个文件，解码文本约为二进制的 20 倍，因此解码全部内容每次快照要花费约一 GB，只为显示一次抓取触及的少数文件。exp1 解码了 586 个中的 5 个，共 3 MB。快照本身约 50 MB，所以预算花在解码上，而不是复制上。
- **转储是内联的**（`bmdump dump-inline`）。客户端每次写入都会重新编号其共享对象槽位，因此原始转储会把真正的变更埋在数百行 `shared[114]` → `shared[143]` 之下。内联把 exp1 从一面噪声墙变成 581 行变更且零槽位抖动。如果你专门想看共享布局，可用普通 `bmdump dump <file>` 手动操作。

即便如此，diff 的大部分仍是 EVE 重新盖上它所重写键的时间戳——exp1 的 581 行变更中有 467 行是纯时间戳。只想看实质内容：

```
tools\capture-diff.ps1 -Label after-a -Against staged-1 | Select-String -NotMatch '^[+-]\s+\d+L\s*$'
```

这把 exp1 的读出降到 114 行。注意脚本在 diff 非空时退出码为 1——这是 git 自身 `diff --no-index` 的约定，不是失败。

这也顺带给出本计划的横切门，见 §7。

## 4. 会话 A

### Phase 1——离线预置（客户端关闭）

预置所有不依赖会话 A 将要发现之内容的编辑器写入。在每个角色登出时保存该角色的文件（它们全部登出——客户端已关闭）。然后运行 `capture-diff.ps1 -Label staged-1 -Against baseline`，肉眼确认 diff 只包含你打算写入的内容。

**在 A1 上——neocom + 布局 + HUD（角色级）：**

- 给一个窗口设置按窗口的 **pinned** 标志。

**在 A2 上——批量目标：** 什么都不做。它在 Phase 1 也会收到一份复制：稍后在账号 B 上，把 **Layout** 方面 A1 → A2（带着 neocom 栏）和 **Keybinds** 方面 A1 → A2 批量复制过去。

**在 A3 上——不触碰。** 对照组：EVE 对编辑器从未保存过的文件做了什么，就是"客户端是否自行重写了它"的基线。

**在账号 A 上（账号级）：**

## 7. 横切门

在**每次**会话之后、查看任何单个功能之前，对每个文件运行。它是对抓取 diff 的一次读取：

- **EVE 到底接受了这个文件吗？** 被拒绝的设置文件不会报错——客户端悄悄兜底到默认值。任何角色的整个布局或总览回退，都意味着编解码器、重共享遍历或某个结构编辑产生了客户端不愿读取的东西，这在本文档中优先级高于其他一切发现。
- **EVE 保留了我们的值，还是重写了它们？** 客户端在自己退出途中重写（而不是按我们写的留着）的键，意味着编辑器写入了一个*合法但非规范*的结构。角色 A3——编辑器从未触碰——是客户端自发重写什么的对照。
- **我们没碰过的东西变了吗？** 重排无关子树的结构编辑是 `reshare` 遍历最可能产生的失败模式，没有任何自动化测试能看到它。
